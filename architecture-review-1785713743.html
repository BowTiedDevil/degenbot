Deepening opportunities in the degenbot pump & state-accuracy core

Exploratory scan focused on the recent hot spots: the pump lifecycle and the solver-state accuracy tripwire — the areas the live-debug session (docs/exploration-live-debug-session.md, 2026-08-02) and the last ~40 commits keep returning to. The codebase is already heavily and deliberately architected (ADR-001…020; CONTEXT.md carries a rolling review log); this report only surfaces what is still open, and marks where a candidate refines rather than re-litigates a recorded decision.

Candidate 1

Deepen the pump's recovery concern out of the delivery loop

Strong

Files

  • bot_core/block_pump.rs (~4k loc + ~2.3k test)
  • bot_core/block_clock.rs · solve_coordinator.rs

Vocabulary

The BlockPump module (the ADR-008 block state machine + its resilience layer) has an interface barely smaller than its implementation — a shallow module whose recovery knowledge has no locality: it is smeared across one giant async loop.

Problem — recovery is a pile of inline heuristics, not a seam

Every live-session failure class so far produced a new inline patch in the same loop: the FSM recovery_anchor reset (BQ7ZBC), the header-staleness watchdog, the logs-silence watchdog, the PanicLateForward unreliable-WS branch, the AV42C7 solver-state gate, the auto-backfill resets (J3FMDO/DFQYM5). The 2026-08-02 session saw two distinct classes — WS disconnect (FSM recovery) vs WS slow-but-connected (state lags 4–37 blocks) — and the response was a fresh patch each time (a clean-shutdown flag replacing a wedging panic!). The deletion test answers "would extracting recovery concentrate complexity or just move it?" — the loop currently holds delivery and recovery decisions tangled together, so deleting the recovery branches would concentrate the remaining loop; the complexity wants a discrete home.

Solution — delivery keeps "what happened"; a policy owns "what to do"

Split the loop's delivery FSM (observe header/log → catalog anomalies) from a narrow delivery-recovery seam: a DeliveryPolicy adapter that, given a typed anomaly (HeaderStall, LogSilence, LateForward), returns a decision (RecoverByBackfill / CleanStop) against a small action interface (re-fetch dropped logs, stop). This is delivery-only — it reconciles dropped WS logs, never the scalar state a hop solves on (that repair is out of scope, per the tripwire posture in Candidate 2). Delivery stays in block_pump.rs; all recovery policy concentrates in one module with one test surface.

Benefits

  • Locality — every recovery heuristic (watchdogs, anchors, gate reaction) concentrates in one place instead of threading through a 4k-line loop; the wedging/backlog classes become unit tests of the policy, not giant integration cases.
  • Leverage — a new failure class (e.g. slow-connected lag) is a new policy arm, not a new inline branch; policy is swappable per-deployment without touching delivery.
  • Testability — drive the policy seam with a fake sink/provider in milliseconds; no tokio stream choreography required to reason about recovery.

ADR alignment — refines, does not re-litigate.

ADR-008 already designs one recovery ("Edge B backfill" on WS drop) and the state machine's monotonicity rules. This candidate adds the delivery-resilience policy above that state machine — it does not touch the tombstone/monotonicity rules, does not re-sync scalar pool state (that is the tripwire's domain — see Candidate 2), and stays limited to Edge-B log backfill + clean stop.

Candidate 2

Extract the state-accuracy tripwire into one discriminating module

Strong

Files

  • bot_core/solver_state_verifier.rs
  • bot_core/liquidity_verifier.rs
  • sim-revert diagnostics (revm inspectors)
  • degenbot-rpc::abi (the shared probe home)

Vocabulary

The accuracy check is a tripwire — it must fail fast, loud, and discriminately. Today the detection is real but smeared across three verifiers with no shared seam, so the failure class is decoded by hand each time. No auto-repair, ever.

Problem — a correct tripwire that is fragmented and undiscriminating

The AV42C7 gate already fails fast and loud — that is the right shape. What is missing is fidelity: the divergence is surfaced as a scalar mismatch with no classification, so root-causing the 2026-08-02 class (is this a missed log, an unhandled reorg, a storage-mutated pool, or plain WS-delivery lag?) is answered by manual archaeology — the write-up literally leaves “discriminator is open.” The tripwire's only job is to make the bug cheap to solve, and today it does not name the class. Three verifiers copy the same on-chain-diff shape into three stop/panic reactions; two adapters doing the same probe on different triggers is the classic signal that a real seam is hiding here.

Scope guardrail — this is a detector, not a healer.

Divergence is a defect to be solved, never an input to smooth over. The tripwire must not re-sync pools, apply missed swaps, or treat staleness as recoverable input. It detects, classifies, and stops loudly — so the underlying state-tracking/decoding bug gets root-caused. Any hidden “heal-on-detection” would mask exactly the bugs this module exists to surface.

Solution — one tripwire module, typed verdict, loud stop

Extract a single state-accuracy tripwire: probe the canonical on-chain scalar state through the shared degenbot-rpc::abi home → produce a typed verdict that discriminates the failure class (MissedLog / UnhandledReorg / StorageMutated / DeliveryLag{blocks}) → fail fast and loud (stop-only) with the class plus a root-causing breadcrumb. The three verifiers converge on one verdict type and one probe shape; the loop keeps only the trip and the exit, none of the classification noise.

Benefits

  • Locality of diagnosis — all accuracy probing + classification concentrates in one module; the three verifiers converge on one verdict, and the chain-probe home (degenbot-rpc::abi) is the single backend (ADR-003 cross-consumer infrastructure).
  • Leverage — a divergence trips into a named class instantly instead of a scalar diff to decode by hand — closing the exact “discriminator is open” gap from the live write-up.
  • Testability — verdict classification is a pure function of before/after state, unit-testable without chain access; trip speed and loudness are directly assertable.

ADR alignment — extends AV42C7; no auto-repair, no conflict.

The AV42C7 gate is already a fail-fast stop-only check; this candidate deepens the same intent (discriminate + rename the defect) and realises ADR-003's “onchain probe as cross-consumer infrastructure.” It aligns with the fail-fast / accuracy-oracle posture of ADR-020 — and explicitly declines the repair path, so it never re-establishes the smoothing this review ruled out.

Candidate 3

The composer's interface can't express "take what's actually there"

Worth exploring

Files

  • executor/composers.rs (three_hop_v3_v4_v3)
  • solvers V4 simulate_swap / Tier-3 oracle

Vocabulary

The composer module couples solver-math exactness to executor safeness: its interface assumes predicted == actual, and a 1-wei divergence reverts the whole path.

Problem — a silent coupling with an implicit invariant

The 2026-08-02 session found V4's on-chain swap returns 1 wei less than v4_simulate_swap on a fee-1 pool, and the composer's enc_v4_take_compact(…, predicted) then "takes" 9586 USDC where only 9585 exists → ERC20: transfer exceeds balance → whole path reverts. The module's interface cannot express a min(predicted, available) take; that surfaced only as a live "fix direction" note, not a first-class option at the seam. This is correctness-adjacent, so it is a weaker deepening — included because it is a genuine, currently-open interface gap (implicit invariant: the interface is not as expressive as the executor's real constraint).

Solution

Two honest routes: (a) a Tier-3 make-v4_simulate_swap-byte-exact effort so predicted == actual and the existing interface becomes sound (the deep fix — ADR-020 territory); or (b) let the composer express a floored take (min(predicted, available)) and re-size the path to preserve v3c's IIA — a defensiveness floor at the seam, at the cost of the IIA tradeoff the live note flags. Recommend mostly (a), with (b) as the load-bearing floor.

Benefits

  • Leverage — the executor stops mis-routing/taking on sub-wei divergence; fewer wasted reverts on tiny/fee-1 pools.
  • Locality — the "predicted vs actual" decision moves to the seam instead of a buried did-you-know note.
  • Testability — a Tier-3 oracle slice already gates byte-exactness; a seam-level floor is directly testable in composers` parity tests.

ADR alignment — aligns with ADR-020 (Tier-3 accuracy oracle).

The byte-exactness route is exactly the ADR-020 Tier-3 probe (Rust math + solver === on-chain Swap event). No contradiction — this is an open 2LTKVO-family item, not a settled decision.

Top recommendation

Start with Candidate 2 — it is the smallest, highest-leverage move, and the one whose design intent is settled. Under the tripwire posture, extracting the state-accuracy module makes the codebase's most recurring live failure class cheap to root-cause instead of decode-by-hand, and it converges three verifiers onto one discriminator. It is stop-only, so it never reintroduces the auto-repair this review ruled out.

Candidate 1 stands apart, afterward, as a pure delivery-recovery seam. It reconciles dropped WS logs (Edge-B backfill) and addresses the wedging/backlog classes — it never re-syncs scalar pool state, so it does not conflict with the tripwire posture. The two strong candidates are independent, not one seam: #2 makes a divergence a bug you can solve, #1 makes the pump's delivery recover.

Candidate 3 is genuine but is mostly a Tier-3 correctness effort already tracked (2LTKVO/ADR-020); treat it as the load-bearing floor, not the first move. Both strong candidates refine recorded decisions (ADR-008 Edge-B / AV42C7) rather than re-litigating them.
