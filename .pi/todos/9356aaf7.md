Currently, Python pool objects (UniswapV2Pool, UniswapV3Pool, UniswapV4Pool) hold mutable state (reserves, tick data, sqrt price) that is duplicated in the Rust engine after registration. After registration, the Python pool goes stale — the Rust engine's pump updates its own copy every block while nobody reads the Python pool's mutable state.

In the future architecture where Rust is the sole state owner, Python pool objects used by the engine should become lightweight structs carrying only:
- Immutable metadata needed for swap encoding (addresses, fee, tick_spacing, pool_id, hook_address, pool_key)
- Registration data (fetched once via RPC, passed to `register_pool`, then discarded)

The mutable state slot should be eliminated from the Python side entirely for engine-managed pools.

**Tension identified**: The existing pure-Python architecture held all state in pool objects. The Rust engine approach makes Python the "operator" layer. This cleanup resolves the dual-state tension.

**Dependencies**: NOT on the critical path for rolling-start. Current dual-state works correctly (Python state is authoritative at registration time, then Rust takes over).
