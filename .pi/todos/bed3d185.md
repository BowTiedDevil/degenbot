Add `register_and_solve_path()` to `UniswapEngine` that atomically:
1. Registers the path (inserts into `paths`, `pool_to_paths`)
2. Resolves the path immediately
3. Solves the path immediately
4. Appends profitable result to `self.results`
5. Adds path_id to `pending_new_paths: HashSet<u64>` (so `rebuild_and_solve_affected` can merge it)
6. Returns (path_id, Option&lt;SolvePathResult&gt;)

The existing `register_path` remains for use before the pump is active (when `initial_solve` would have been called in bulk). `register_and_solve_path` is used when the engine is already running.

**Decisions**: 
- Eager solving at registration time
- Results written to `self.results` immediately (Option A from Q19)
- `pending_new_paths` set tracks newly-registered paths so `rebuild_and_solve_affected` can merge them instead of discarding
- One-block staleness window is acceptable — next `process_block` will re-solve if affected pools changed
- Minimum-2 paths requirement stays
