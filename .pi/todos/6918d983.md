## Summary
Partially done: V3_SWAP_DELTA and ERC20_XFER_BALANCE are now importable but not yet used in path encoders.

### What's Available
- `enc_v3_swap_delta(pool_idx, zfo, recipient_idx)` — 4 bytes. Reads amount from PM exttload (amount owed to V3 pool from callback params). Only usable when V3 is inside a V4 unlock and the owed amount is deterministically known from the callback.
- `enc_erc20_xfer_balance(token_idx, recipient_idx)` — 3 bytes. Transfers executor's entire balance of a token. Useful for sweep operations.

### Why Not Used Yet
- V3_SWAP_DELTA: The current V3 encoders use V3_SWAP_COMPACT with explicit amounts. V3_SWAP_DELTA reads from PM exttload, which requires the V3 swap to be inside a V4 unlock context. Most V3 swaps happen outside V4 unlock (they're triggered by V3 callbacks), so V3_SWAP_DELTA has limited applicability. The only case where V3 is inside V4 unlock is in V4→V3 paths, but those already use V3_SWAP_COMPACT with the amount from the forward token output.

- ERC20_XFER_BALANCE: Replacing `enc_erc20_transfer(token_idx, recipient_idx, amount)` (15 bytes) with `enc_erc20_xfer_balance(token_idx, recipient_idx)` (3 bytes) saves 12 bytes per call, but is only safe when the executor's entire balance of that token should be sent. For flash loan repayments, the exact amount matters (not the full balance). For profit sweeps after all swaps, the exact amount is also usually known.

### When to Use
- V3_SWAP_DELTA: Inside V4 unlock when V3's input amount is from callback delta
- ERC20_XFER_BALANCE: When sweeping remaining balance after all operations are done (e.g., WETH flash repayment when the executor holds exactly the right amount)
