## Problem

Each `apply_log` call allocates 3 `HashSet<u64>`s (`affected_pools_v2`, `v3`, `v4`) to collect dirty pool keys, then another `HashSet` for affected paths. In the eager model, `apply_log` is called per-WS-log. Worse, the returned `HashSet<u64>` of affected path IDs is never used by the pump — it's computed and immediately discarded.

Location: `rust/src/optimizers/uniswap_engine.rs` → `apply_log` (~line 391)

## Fix

Remove the 3 intermediate `affected_pools_v*` HashSets and the return value. The dirty sets (`self.dirty_v2/v3/v4`) already accumulate the pool keys — that's all the pump needs. The affected-paths computation can move into `rebuild_and_solve_affected` where it's actually needed (it already does its own reverse-index lookup from the dirty sets).

If the return value is needed for testing, add a separate `apply_log_and_get_affected_paths` method.

## Current Code Pattern

```rust
pub fn apply_log(&mut self, log: &Log, block_number: u64) -> HashSet<u64> {
    let mut affected_pools_v2: HashSet<u64> = HashSet::new();  // ← allocated per call
    let mut affected_pools_v3: HashSet<u64> = HashSet::new();  // ← allocated per call
    let mut affected_pools_v4: HashSet<u64> = HashSet::new();  // ← allocated per call
    // ... route to sub-engines, collect keys ...
    let mut affected_paths: HashSet<u64> = HashSet::new();  // ← allocated per call, never used by caller
    // ...
    affected_paths  // ← returned but pump ignores it
}
```
