## Problem

Each V3/V4 path resolution calls `build_int_v3_sequence` → `compute_tick_ranges` → `get_sqrt_ratio_at_tick_internal` (U256 iterative multiplication) for every tick boundary. For a hot pool appearing in many paths, the same tick math is recomputed for every path. With 10 tick ranges per direction × 2 directions per pool × N paths per pool, this multiplies quickly.

Locations:
- `rust/src/bot_core/tick_bitmap.rs` → `compute_tick_ranges` (~line 257) — calls `get_sqrt_ratio_at_tick_internal` per tick boundary
- `rust/src/optimizers/v3_block_engine.rs` → `build_int_v3_sequence` (~line 245)
- `rust/src/optimizers/v4_block_engine.rs` → `build_int_v4_sequence` (equivalent)

## Fix

Cache `sqrt_price_x96` per tick on `V3PoolState`/`V4PoolState`. When `apply_swap` updates the tick, invalidate only the pool's own cache. `compute_tick_ranges` reads from cache instead of calling the function. Since tick values are bounded (±887272), a `HashMap<i32, U256>` cache per pool would work. Approximate savings: ~10 × `get_sqrt_ratio_at_tick_internal` calls per path per solve, replaced by HashMap lookups.

Alternative: pre-compute and cache the sequences on pool state (invalidate on `apply_swap`/`apply_liquidity_update`), so `resolve_path` just reads a cached seq instead of rebuilding from tick_data each time.
