**Master: `TODO-215e9e66` (ADR-006).** Deps: slice 1. Addresses ADR-006 D3.

**Goal.** Pool registration becomes a `Bot` concern ONLY; the engine never constructs pools. Today the engine re-registers pools into its core (separate from the `PyBot`-registered library pools); once slice 1 unifies the Arc, double-registration would hit `Bot`'s duplicate-panic (`register_v2/v3_pool` panic, `register_v4_pool` `Err`). D3 deletes the engine-level registration; the engine discovers pools at `register_path` time by resolving `pool_id`s against the associated `Bot`.

**Rust work.**
- Delete the three methods at `rust/src/optimizers/uniswap_engine/mod.rs:449/478/489` (`register_v2_pool`, `register_v3_pool`, `register_v4_pool` — they delegate to `self.core.lock().register_*`).
- The engine's `register_path` (in `lifecycle.rs`) currently takes `Vec<MixedPoolRef>` = `(hop_type, pool_key, zero_for_one)` where `pool_key` is the engine's own pool_id (allocated at engine `register_v*`). Re-shape to take the **`Bot`'s `pool_id`s** (which the builder already obtained from `PyBot.register_v2_pool` → stashed on the Python companion's `pool_id` accessor) and resolve each against the shared `Bot` `read()` guard — verifying the pool exists + its family matches the claimed `hop_type`. Reject with a clear error if a `pool_id` isn't registered in the associated `Bot`.
- V2 dual-orientation: today `register_v2_pool` returns the forward `pool_id`; reverse = `+1`. Confirm `register_path` can derive both orientations from a single `Bot` `pool_id` (it already can — `Bot` stores one `PoolEntry` per pool per ADR-003; orientation is resolved at solve time from `zero_for_one`). So `register_path` takes `(pool_id, zero_for_one)` per hop, no forward/reverse duplication.

**Python work (preliminary; full migration is slice 9).**
- `examples/eth_backrun_v2_v3_v4_rust.py`: `engine_registry.register_v2_pool(pool)` etc. (lines ~980-985) → `engine.register_path([(pool.pool_id, zero_for_one), ...])` reading `pool.pool_id` off the Python companion. (The companion's `pool_id` accessor already exists from ADR-005 slice 4 — confirm it's exposed.)

**Tests.**
- Red first: a test asserting `engine.register_v2_pool` no longer exists (compile error → remove the test's call site).
- Green: register a pool via `PyBot`, then `engine.register_path([(pool_id, zfo)])` resolves it; assert the path solves. A negative test: `engine.register_path([(bogus_pool_id, zfo)])` raises the not-registered error.
- Existing engine path-solving tests updated to register via `PyBot` first, then `register_path`.

**Acceptance.** `just test-all` green; engine `register_*` methods deleted; engine intake is `register_path` resolving `pool_id`s; no double-registration possible (panic surface removed, not papered over). `Bot::register_*` remains the sole pool-construction path on both the Rust-only and Python-driven flows.

## Progress log

- **DONE, green:** `register_path`/`register_and_solve_path` intake is now
  `Vec<PoolHop> { pool_id, zero_for_one }` → `Result<u64, String>`. The engine
  derives each hop's family (`hop_type`) from the associated `Bot`'s
  `PoolEntry` variant (`derive_hop_type` helper) and **rejects** any `pool_id`
  not registered in the `Bot` with a clear error (ADR-006 D3). `MixedPoolRef`
  becomes the internal storage representation (kept); `PoolHop` is the public
  intake.

- **Engine `register_v2/v3/v4_pool` (mod.rs) deleted** from the production API,
  relocated to a `#[cfg(test)] impl` as no-pyo3 test helpers (they delegate
  straight to `Bot::register_*` via `core`). Production code never registers
  pools via the engine.

- **py_binding `register_v2/v3/v4_pool` pymethods KEPT + rewired** to register
  via `engine.core.write().register_*` (the `Bot`) instead of the deleted
  engine methods. This preserves the Python API + `test_uniswap_arb_engine.py`
  (43 sites). Rationale: the todo's literal scope deletes only the mod.rs
  engine methods; the pymethods are the PyO3 surface and delegate to the same
  `Bot` (single registry, D3's intent). For a `py_bot=`-constructed engine the
  caller must NOT also register via `PyBot` (would panic — documented).

- **V2/V4 `fwd_key + 1` reverse-orientation hack removed.** Pre-ADR-003 the V2
  engine allocated forward+reverse ids; `Bot` is 1-id-per-pool, so `+1` pointed
  at the *next* registered pool (latent bug). `register_path` now takes
  `zero_for_one` per hop; one `pool_id` serves both orientations.

- **Python API:** `PyUniswapArbEngine.register_path`/`register_and_solve_path`
  take 2-tuples `(pool_id, zero_for_one)` (was 3-tuples with `hop_type`).
  `test_uniswap_arb_engine.py` updated (3-tuple→2-tuple).

- **Example (`eth_backrun_v2_v3_v4_rust.py`):** minimal rewire —
  `EngineRegistry.register_path` builds 2-tuples + drops the `+1`. Dead
  `_hop_type_str` helper removed. The example still uses a STANDALONE engine
  (`UniswapArbEngine()`, own `Bot`) — no double-registration panic (separate
  Bots). Full dual-Bot dissolution (share `py_bot=` core, drop
  `engine.register_v*`, add `engine_pool_id` accessor) is **slice 9**.

- **Test fixes forced by the new reject-missing-pool behavior:**
  - `missing_v2_pool_makes_path_invalid` — was vacuously passing (referenced
    non-existent `pool_key: 0`; `Bot::next_pool_id` starts at 1, so 0 never
