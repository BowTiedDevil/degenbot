**Deferred from slice 7 (DEX subclass collapse).** Spun out per the user's call: Aerodrome is a unique design that may not collapse neatly into the V2 `LiquidityPool` companion; investigate architectural designs that more cleanly support this style of pool separately.

**Why Aerodrome doesn't fit the slice-7 collapse.** Unlike `SushiswapV2Pool`/`PancakeswapV2Pool`/`SwapbasedV2Pool` (hollow — just a `variant` ClassVar + `FEE`/`RESERVES_STRUCT_TYPES`) and `CamelotLiquidityPool` (a `UniswapV2Pool` subclass since slice 4, divergence = `CamelotPoolCalc` solidly-stable strategy + a `to_hop_state` branch), `AerodromeV2Pool` is **not a `UniswapV2Pool` subclass at all**. It's a fully-independent 564-line pure-Python pool — `class AerodromeV2Pool(PublisherMixin, PoolPickleMixin, AerodromeV2PoolStateMixin, AerodromeV2PoolCalc, AbstractLiquidityPool)` — with its own:
- State mixin (`AerodromeV2PoolStateMixin` + `AerodromeV2PoolState`), own `StateCache`, own `external_update`/`simulate_swap`/`simulate_swap_for_output`/`to_hop_state`/`build_swap_amount`.
- Own log decoder (`_decode_aerodrome_v2_sync`) + `LOG_HANDLERS`.
- Per-pool `stable: bool` flag (volatile vs stable pool — resolved on-chain via `stable()`; drives a solidly-stable-vs-constant-product calc branch).
- Per-pool on-chain `fee` (resolved via `factory.getFee(address, stable)` — not a DEX-wide constant; the preset carries only a typical default + the denominator).
- `get_pool_identity_values(...)` batch-fetches factory/token0/token1/stable/fee/reserves in one round-trip.
- `swap_is_viable` (state-level swap admissibility check) — not present on `UniswapV2Pool`.
- No `PyLiquidityPool` handle (deferred from slice 4's companion conversion — the slice-4 work that converted `UniswapV2Pool`/`CamelotLiquidityPool` to companions deliberately skipped Aerodrome).

**The architectural question.** The Polars three-layer companion (`PyLiquidityPool` + Rust `V2PoolState`) is a 2-token constant-product pattern. Aerodrome adds three things that don't fit:

1. **Solidly-stable-vs-constant-product duality.** A single pool is volatile OR stable (per-pool, on-chain). The stable path uses a different invariant (`calc_exact_in_stable` — same `solidly_stable` calculations module Camelot stable uses, but with default k/get_y vs Camelot's k_camelot/get_y_camelot). This isn't a DexIdentity preset problem — it's a pool-state-shape problem: the *same Rust `V2PoolState`* (reserves0/reserves1) backs both branches, but the calc dispatch is per-pool.
2. **On-chain fee resolution.** Fees aren't a DEX-wide constant — `factory.getFee(address, stable)` returns the per-pool fee at query time. The `DexIdentity` preset's `fee_token0/1` are "typical defaults," not the actual fee. Real fees must be fetched (builder I/O) and stored as pool state — not on the immutable `dex` identity. So `V2PoolState.fee_token0/1` (Rust) needs to be per-pool-mutable OR the companion carries the resolved fee Python-side.
3. **`get_pool_identity_values` batch fetch.** Aerodrome's identity isn't derivable from `(chain_id, factory)` alone — `stable()` + `factory.getFee(address, stable)` are per-pool reads. The registry's `(chain_id, factory) → class` (or `→ DexIdentity`) resolution doesn't close the loop; the builder must probe the pool on-chain to resolve (stable, fee, reserves) before construction.

**Candidate architectures to evaluate (this is the investigation's deliverable):**

- **A. Strategy-on-companion (minimal lift).** Convert Aerodrome to a `PyLiquidityPool` companion like Camelot: `LiquidityPool` (or an `AerodromeV2Pool` companion subclass) carries `stable: bool` + a resolved `fee` as Python-side pool state (set at construction from builder's on-chain `getFee` call), wires the solidly-stable calc strategy when `stable`. Rust `V2PoolState` keeps `fee_token0/1` as the resolved per-pool value (already mutable via `register_v2_pool`'s params). The `get_pool_identity_values` batch stays a builder concern. **Question to answer:** does this preserve the on-chain `getFee` parity + the stable calc + `swap_is_viable`?
- **B. Separate Rust state variant.** Like V3/V4 have their own `PoolEntry::V3`/`::V4`, Aerodrome could get `PoolEntry::SolidlyStableV2` — a variant holding reserves + stable flag + resolved fee + the k/get_y function pointers (or an enum selecting the solidly-stable flavor). Heavier Rust lift; cleaner separation; may be overkill if (A) holds.
- **C. Third-family framing.** Treat Aerodrome-V2 as the third "family" alongside Curve/Balancer (ADR-003's "third family"): a Solidly-invariant family that gets its own companion + own Rust state (when it warrants Rust backing). Matches the "third-family" language already in ADR-003/005.
- **D. Hybrid: companion + per-pool fee override.** Companion carries `dex: DexIdentity` (deployment identity — factory/deployer/init_hash, which IS DEX-wide) + a separate per-pool `fee: Fraction` + `stable: bool` resolved at construction. Strategy wired off `stable` (like Camelot). The preset's `fee_token0/1` are only fallbacks when the builder doesn't fetch (rare). **This is roughly what slice 7a's `LiquidityPool` will do for Camelot anyway** — so (A) and (D) converge.

**Deliverable.** A short design memo (in the Aerodrome CONTEXT.md or a new ADR) choosing one of A/B/C/D, with the trade-offs. Then implement as a follow-up slice to slice 7 (depends on slice-7's `LiquidityPool` + `DexIdentity` landing first — those are the foundation either way). NOT blocking slice 7 (slice 7 leaves Aerodrome untouched as its own class).
