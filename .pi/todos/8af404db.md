## Problem
`ResolvedMixedPath` uses 6 parallel `Vec<Option<T>>` to represent resolved hops. The hop type determines which Vec entries are `Some`. This is fragile — wrong index = silent wrong data. The solver must pattern-match on `hop_types[i]` then reach across to the right Vec. Pushing a V2 hop requires filling 6 slots, 4 of them `None`/zero.

## Files
- `rust/src/optimizers/uniswap_engine.rs` — `ResolvedMixedPath` struct (lines ~155–180)

## Current struct
```rust
struct ResolvedMixedPath {
    hop_types: Vec<HopType>,
    v2_hops: Vec<Option<IntHopState>>,
    v3_sequences: Vec<Option<V3TickRangeSequence>>,
    int_v3_hops: Vec<Option<IntV3TickRangeHop>>,
    int_v3_sequences: Vec<Option<IntV3TickRangeSequence>>,
    base_hops: Vec<HopState>,
    valid: bool,
}
```

## Proposed replacement
```rust
enum ResolvedHop {
    V2 {
        state: IntHopState,
        base: HopState,
    },
    V3 {
        seq: V3TickRangeSequence,
        int_hop: IntV3TickRangeHop,
        int_seq: IntV3TickRangeSequence,
        base: HopState,
    },
    V4 {
        int_seq: IntV3TickRangeSequence,
        base: HopState,
    },
}

struct ResolvedMixedPath {
    hops: Vec<ResolvedHop>,
    valid: bool,
}
```

## Impact on consumers

### `resolve_path()` (currently pushes 6 slots per hop)
**Before:**
```rust
HopType::V2 => {
    resolved.hop_types.push(HopType::V2);
    resolved.v2_hops.push(Some(hop_state.clone()));
    resolved.v3_sequences.push(None);
    resolved.int_v3_hops.push(None);
    resolved.int_v3_sequences.push(None);
    resolved.base_hops.push(base);
}
```
**After:**
```rust
HopType::V2 => {
    resolved.hops.push(ResolvedHop::V2 { state: hop_state.clone(), base });
}
```

### `solve_path()` (currently reads individual Vecs)
**Before:**
```rust
let all_v2 = resolved.hop_types.iter().all(|&t| t == HopType::V2);
if all_v2 {
    let int_hops: Vec<_> = resolved.v2_hops.iter().filter_map(Option::as_ref).cloned().collect();
    ...
}
```
**After:**
```rust
let all_v2 = resolved.hops.iter().all(|h| matches!(h, ResolvedHop::V2));
if all_v2 {
    let int_hops: Vec<_> = resolved.hops.iter()
        .filter_map(|h| match h { ResolvedHop::V2 { state, .. } => Some(state.clone()), _ => None })
        .collect();
    ...
}
```

### `solve_mixed_path_int()` (currently indexes `v2_hops` and `int_v3_sequences`)
**Before:**
```rust
crate::optimizers::mobius_v3_int::exact_solve_mixed_path_n(
    &resolved.v2_hops,
    &resolved.int_v3_sequences,
    &hop_order,
)
```
**After:** Build `Vec<Option<&IntHopState>>` and `Vec<Option<&IntV3TickRangeSequence>>` from the enum for the solver, or modify the solver to accept `&[ResolvedHop]` directly.

### V4 int128 guard
**Before:**
```rust
for (i, hop_type) in resolved.hop_types.iter().enumerate() {
    if *hop_type == HopType::V4 {
        let consumed = r.consumed_inputs.get(i).copied().unwrap_or(U256::ZERO);
        ...
    }
}
```
**After:**
```rust
for (i, hop) in resolved.hops.iter().enumerate() {
    if matches!(hop, ResolvedHop::V4 { .. }) {
        let consumed = r.consumed_inputs.get(i).copied().unwrap_or(U256::ZERO);
        ...
    }
}
```

## Alternative: modify the solver too?
The mobius solver functions (`exact_mobius_solve`, `int_solve_cl_path`, `exact_solve_mixed_path_n`) currently accept `&[IntHopState]` and `&[IntV3TickRangeSequence]`. We could either:
1. **Adapter layer**: build the solver's expected input types from `&[ResolvedHop]` before calling — minimal solver changes
2. **Solver rework**: make the solver accept `&[ResolvedHop]` directly — larger change, mixes dispatch into the solver

Option 1 is safer and more incremental. The adapter is cheap (O(n) where n is hop count, typically 2-3).
