**Master: `TODO-215e9e66` (ADR-006).** Deps: slice 4. Addresses ADR-006 (optimistic per-event journal rollback, Q8-Q9 resolved).

**Goal.** Replace the bulk `engine.handle_reorg(block)` ADR-003 Option α path with optimistic **per-event** journal rollback. On EVERY `removed: true` log for pool P at block `B`, `ReorgCoordinator` calls `ReorgJournal::restore_before_block(B)` for P, writes the landed-at state into current `BotState`, fires the **same** `on_pool_state_updated(P)` notification as a forward update — no separate `on_reorg` method. The WS `removed: true` replay ordering is unspecified by any standard, so the design relies on `restore_before_block`'s idempotency + order-insensitivity (verified in `state_history.rs:340-375`: newest `< B` → no-op; newest `≥ B` → while-loop pops every `back().block() >= B`; chronological / reverse-chronological / out-of-order all resolve correctly).

**Rust work.**
- New `pub(crate) struct ReorgCoordinator` (or a method on `LogDispatcher`/`Bot`) watching logs for `log.removed == true`. For each: identify the target `pool_id` + `block` (the removed event's own block, present on every log), call `BotState`'s `restore_before_block(B)` for that pool (V2 path; V3/V4 via the existing `v3/v4_restore_before_block`), write the returned landed-at state into current `BotState`, then `log_dispatcher.notify(pool_id)` (the same path slice 4 uses for forward notifies).
- The removed event's CONTENT is unused — only its block number + pool identity (the journal's stored "before" values are the source of truth).
- The `max_depth` hard limit is unchanged: a `removed: true` event whose block is below the journal's earliest surviving delta hits `Err(NoStatePriorToBlock)` → fail-stop (the existing behavior; do NOT relax the bound).
- Retire/delete the bulk `engine.handle_reorg(block)` method (in `event_routing.rs` / wherever it's invoked from the pump's `removed: true` branch). The pump's reorg path now routes to `ReorgCoordinator` per-log instead.

**Tests.**
- Optimistic rollback, all orderings:
  - Chronological removed (D then C, D > C): two single-block unwinds, lands at pre-C.
  - Reverse-chronological (C then D): first call pops both, second is no-op; lands at pre-C.
  - Out-of-order across pools: each pool restores independently against its own journal.
- Idempotency: duplicate removed events at the same block for the same pool → not-panic, no-op.
- `max_depth` fail-stop: synthesize a reorg below the journal's earliest delta → assert `NoStatePriorToBlock` + fail-stop (unchanged from today).
- Notify path: reorg fires the SAME `on_pool_state_updated(P)` as forward → engine dirties + re-solves at drain (no distinct reorg path in the engine).
- V3/V4 tick-priors: assert the fixed multi-priors-accumulation (oldest-wins) survives the per-event path.

**Acceptance.** `just test-all` green; bulk `handle_reorg` deleted; reorg is a burst of per-pool `on_pool_state_updated` notifies driven by optimistic per-event `restore_before_block`; works under any arrival ordering; `max_depth` bound preserved. Update `rust/CONTEXT.md` {Reorg Journal} term's "LIVE" implementation-status line + `rust-owned-bot.md` if they reference the bulk path.
