## Summary
Update the eth_backrun_v2_v3_v4_rust.py bot to work with the new cmd_executor contract. This covers: runtime bytecode update, ABI change, constructor parameter changes, and the `initialize()` warmup call.

## Changes

### 1. Update Runtime Bytecode File
The file `contracts/cmd_executor_runtime_bytecode.txt` must be replaced with the NEW contract's runtime bytecode. The new contract requires immutables baked in:
- WETH_ADDR (immutable)
- POOL_MANAGER_ADDR (immutable) 
- OWNER_ADDR (immutable)
- USER0_ADDR (immutable) — typically USDC
- USER1_ADDR (immutable) — typically WBTC

The bytecode must be built from the new contract source with these values hardcoded.

### 2. New Constructor Parameters
```python
# Old: __init__(weth, pool_manager)
# New: __init__(weth, pool_manager, user0, user1)

user0 = USDC_ADDRESS  # 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48
user1 = WBTC_ADDRESS  # 0x2260FAC5E5542a773Aa44fBCfeDf7C193bc2C599
```

### 3. Initialize Call After Deployment
The new contract requires `initialize()` to be called once with 2 wei ETH:
```python
# After deployment:
executor.initialize(value=2)  # Warms ERC6909 slot for gas savings
```

### 4. Update INJECTED_EXECUTOR_ADDRESS
If the injected address changes, update the constant. When INJECT_EXECUTOR_CODE=True, the state overrides must:
- Set the NEW runtime bytecode at the injected address
- Fund the executor with ETH (same as before)
- Set WETH balance for the executor (same as before)
- NO additional storage overrides needed — `initialize()` is only for on-chain deployment

### 5. State Override Updates
`build_simulation_state_overrides()` needs minor updates:
- The WETH balance slot may need adjustment if the new contract stores it differently
- The executor ETH balance should be 0 for the new contract (no WETH wrap at construction — it wraps on-demand)
- Actually, for simulation, the executor still needs some WETH balance for V3 auto-pay. Keep the 10 ETH WETH override.

### 6. Executor Identifier Updates
- Update the docstring at the top of the file to describe cmd_executor (not tstore_executor)
- Already partially done — the docstring mentions cmd_executor but references old patterns

### 7. V2 Callback Configurable Fee
The new executor stores per-swap V2 fees in transient storage, enabling mixed-fee V2 paths (e.g., Uniswap 0.3% + PancakeSwap 0.25%). The V2HopInfo already carries `fee: int` — verify this is passed through correctly to `enc_v2_swap_compact()` and `enc_v2_swap_calc()`.
