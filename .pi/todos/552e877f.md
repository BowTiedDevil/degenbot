## Symptom
V3-V2 path occasionally fails with `UniswapV2: K` invariant violation. Only 1 failure out of 131 sim-ok in recent run.

## Root Cause Hypothesis
V2 pool reserves drift between solve time and simulate time. The solver computes `forward_out` and `weth_out` based on reserves at block N, but by the time the simulation runs at block N+1, the V2 pool may have been swapped through by other actors, changing its reserves. The V2 callback repays `optimal_input` WETH, but the K invariant check uses current reserves which no longer match.

## Key Question
Is this:
1. **Staleness**: V2 pool updated between solve and simulate (normal, expected for non-atomic reads)?
2. **Amount encoding bug**: V2 callback repays wrong WETH amount (e.g., `optimal_input` ≠ actual V2 debt)?
3. **V3 forward_data timing**: V3 output differs from `forward_out` → V2 gets wrong USDC input → K fails?

## Debugging Approach
- Log the specific V3-V2 path ID and block number when K failure occurs
- Check if the V2 pool had a Swap/Sync event between solve block and fail block
- Compare V3's `forward_out` (solver prediction) vs V3 actual on-chain output at failure block
- Verify V2 callback's `ERC20_TRANSFER(WETH, v2_idx, optimal_input)` covers the exact V2 debt

## Context
- V3-V2 encoder uses forward_data: V2 flash swap (WETH to executor), V2 callback repays forward to V2, then transfer WETH to V3
- The 1 failure is intermittent — same path succeeds on other blocks
- V3 amountSpecified = optimal_input ✅, V2 flash borrow pattern matches test_cmd_executor_v2v3.py
