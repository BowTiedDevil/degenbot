**Goal.** Apply ADR-005 (Polars-Inspired Three-Layer Architecture) across the codebase: every Rust-owned stateful resource gets the `Bot core → Py* wrapper (Arc<RwLock/shared key) → Python companion` topology. Continues ADR-005 slices 1-2 (already landed: `name=` overrides dropped; `PyPool`→`PyLiquidityPool`, `PyToken`→`PyErc20Token`).

**Current state (post slices 1-2).**
- Rust core `Bot` (`rust/src/bot_core/mod.rs`) owns V2/V3/V4 state in `PoolEntry::{V2(V2PoolState), V3(V3PoolState), V4(V4PoolState)}` + `TokenEntry` map, reorg journals, swap math, swap encoding.
- `PyBot` (`py_bot.rs`) exposes: register/update/journal for V2+V3, `register_token`/`get_token`→`PyErc20Token`, `calculate_tokens_out/in`, `encode_swap`, `get_pool`→`PyLiquidityPool`. **No V4 register/update** (V4 registers via the engine path).
- `PyLiquidityPool` (`py_liquidity_pool.rs`): `calculate_tokens_out/in`, `encode_swap`, `pool_id` getter. **No read getters** (reserves/fee/tokens/factory) — needed before companions can delegate state reads.
- `PyErc20Token` (`py_erc20_token.rs`): `address`/`decimals`/`symbol`/`name` — **complete**.
- Python `Bot` (`src/degenbot/bot.py`, 608 lines) constructs `self._py_bot = PyBot()` at line 90 and **delegates nothing** — all state still in pure-Python pools/tokens via `PoolRegistry`/`TokenRegistry`/`ManagedPoolRegistry`. The companion migration is 0% done on the Python side.
- `UniswapArbEngine` (Rust) holds its own `Arc<Mutex<Bot>>`, registers V3/V4 via snapshot/backfill (`PyUniswapArbEngine.load_v3/v4_snapshot_from_py`, etc.) — a **separate `Bot` instance** from `PyBot`. Dual-state for engine-managed pools is the existing consistent baseline (closes via slice 10).

## Slice 3 (Erc20Token purge) — DONE. Findings that reshape Slides 4-9:

- **~2× construction churn vs. surveyed.** Direct `Erc20Token(...)` sites: ~70 (surveyed ~40), across ~25 files incl. integration tests/conftests/fakes/optimizer tests. Resolved via `sed` construction-swap + a `make_erc20`/`make_ether_placeholder` test helper (`tests/helpers/erc20_factory.py`, idempotent via `get_token`-first because `Bot::register_token` asserts on dup). **Slice 4 (V2 pools) will be WORSE: V2 pools are constructed directly far more often than tokens.** Either budget heavy mechanical churn from the start OR introduce a transitional `LiquidityPool.from_state(...)`-style factory + converse approach before the pure purge. Re-examine the per-slice "small proof-of-concept" expectation for pool companions — they aren't small.
- **Pickle breakage is systemic and reaches the POOL tier.** Tokens hold non-picklable `Py*` handles → `Erc20Token.__getstate__` drops the handle (detached-snapshot unpickled tokens). **Every pool-family slice (4/8/9) will need the same `__getstate__`-drop-the-handle on the pool companion** (pools pickle via `PoolPickleMixin`; their own `PyLiquidityPool` handle is equally non-picklable). The detached-snapshot pattern is now the template — bake it into the slice design from the start rather than discovering it.
- **B-ii confirmed right call for calc.** Slice 3 didn't touch calc (tokens have none); but the pickle issue is exactly why "Rust owns state, Python keeps I/orchestration" must hold the line — don't let the handle leak into pickled graphs beyond the documented detach.
- **`chain_id` getter added to `PyErc20Token`** (Rust) — precedent: companion metadata getters that delegate to `TokenEntry`/state structs land on the `Py*` wrapper as the companion needs them. Expect the same read-getter additions on `PyLiquidityPool` (reserves/fee/factory/tokens) in Slice 4.

Slice 3 commit pending user review of the pickle-detach consequence + the blow-up count.

## Slice 5 DONE — `b6bdeb16` "delegate V2 calc to PyLiquidityPool"

Calc delegation lands for the constant-product path: `UniswapV2PoolCalc.calculate_tokens_out_from_tokens_in` / `calculate_tokens_in_from_tokens_out` route to `self._py_pool.calculate_tokens_out/in(...)` on the NON-override path (Rust reads reserves + fee under one read guard — no Python state read beforehand, so a pump `sync_reserves` can't interleave between calc reads). Override path stays Python so `simulate_*` can hold one snapshot Python-side (slice-4's delta-consistency fix). Camelot/Aerodrome stable strategies remain pure Python (ADR-005 B-ii).

**TDD shape:** 9 new delegation-detection tests in `TestV2CalcDelegation` (`tests/uniswap/v2/test_v2_pool_io_free.py`) — `_DelegateSpy` wraps a `PyLiquidityPool` to record `calculate_tokens_out/in` calls (via `__getattr__` pass-through for state getters), so the tests assert "Rust was hit with the right `(zero_for_one, amount)`" rather than "result matches" (the parity tests already guarantee the math via `test_py_bot.py`). 5 delegation-detection tests red before implementation, 4 happy-path regressions pass.

**Two latent bugs surfaced + fixed:**
1. **Register-time fee-convention mismatch** (the big one). Slice-4's `make_v2_pool`, `V2PoolBuilder`, `CamelotBuilder` all registered `gamma_numerN = fee_tokenN.numerator` (fee semantics — 3 for 0.3% fee). But Rust's `IntHopState` (per its docs + parity tests) treats `gamma_numer` as the RETAINED POST-FEE fraction (`fee_denom - fee.numerator` — 997 for 0.3%). Slice-4 never invoked a Rust calc on a Python-built V2 pool (it routed everything through `simulate_*` which passes an override → Python calc). Slice-5's delegation routes direct no-override calls through Rust → exposes the mismatch: Python returned the correct on-chain `getAmountOut` (564_306_081_156_850_938 ≈ 0.56 WETH for 1000 USDC), Rust-as-registered returned 1_722_257_478_539_954 (~332× too small — exactly the 99.7% fee-as-loss factor). Fixed by registering the complement everywhere a fee Fraction is the source: new `_gamma_complement(fee) -> (fee.denominator - fee.numerator, fee.denominator)` helper in `make_v2_pool`; `fee_token.denominator - fee_token.numerator` in both builders. The `test_py_bot.py` parity tests already used the complement convention (they were the canonical reference).

2. **Slice-4 sentinel leftovers.** `'0xt0'`/`'0xt1'`/`'0xt2'`/`'0xtokenA'`/`'0xtokenB'`/`'0xtokenC'` short non-hex-flagged token sentinels in `tests/arbitrage/test_path/*.py` — slice-4 only caught the `'0xT0'` family (uppercase). `make_v2_pool`'s `register_v2_pool` parses the token address, failing on short sentinels with `ValueError: invalid string length`. Replaced with valid 40-hex sentinels (aaa/bbb/ccc ×40 and 111/222/333 ×40). 69 `test_path/` tests re-enabled.

## Slice 6 DONE — `31ba43bc` "DexIdentity + DEX presets in Rust core (ADR-005 slice 6)"

The standalone-Rust `DexIdentity` registry + 8 `pub const` DEX presets land in the pure-Rust core (zero pyo3 — verified). This is the foundational "standalone constraint" data layer: a future standalone Rust consumer can `cargo add degenbot-core` and construct a Sushiswap V2 pool without any Python import. Exposed via a Python seam (`#[pyfunction] dex_identity(variant)` + frozen `#[pyclass] PyDexIdentity` view) for slice 7's first consumer.

**TDD shape:** 14 Rust unit tests in `dex_identity.rs` `#[cfg(test)]` mod + 9 Python seam tests in `test_py_bot.py::TestDexIdentityPresets`. Red phase = presets set to `Address::ZERO`/`B256::ZERO`/`(0,0)` placeholders → 7 preset-value unit tests fail with `left == ZERO` assertions. Green = fill in the verified Python ClassVar values cross-checked against `src/degenbot/{uniswap,sushiswap,pancakeswap,swapbased,camelot,aerodrome}/__init__.py` `v2_deployments`/`_factory_address` + the FEE/FEE_DENOMINATOR/init-hash ClassVars. The 9 Python tests mirror the same assertions through the FFI seam.

**Design realized:**
- `DexIdentity` struct mirrors the `V2PoolState` field types exactly (`Address`, `(u64,u64)` fees) so slice 7 can feed `register_v2_pool(gamma_numerN=identity.fee_tokenN.0, fee_denomN=identity.fee_tokenN.1, factory=identity.factory, ...)` directly — no convention translation at the consumption point.
- `fee_tokenN: (u64, u64)` = `(gamma_numer, fee_denom)` — the RETAINED post-fee fraction (slice-5 convention). PancakeSwap's `Fraction(25, 10000)` → preset `(9975, 10_000)`. The module doc + field doc + the tests bake this in explicitly to guard against re-introducing the slice-5 bug.
- Added `reserves_abi: ReservesAbi` + `init_hash: B256` fields beyond the literal TODO struct spec — ADR-005 names both ("init hash" + "ABI struct shapes"); the acceptance test checks Pancake's `RESERVES_STRUCT_TYPES`. `init_hash` is NEW data (`V2PoolState` doesn't store it per ADR-005: "identity is NOT a field on V2PoolState").
- Python seam: `#[pyclass(frozen, skip_from_py_object)] #[derive(Clone)] PyDexIdentity` — a COPY view (hex-string addresses, int-tuple fees) cached in a `OnceLock<HashMap>`. `skip_from_py_object` opts out of the deprecated auto-`FromPyObject` that deriving `Clone` on a pyclass triggers. `#[pyfunction] dex_identity(variant)` is case-insensitive kebab lookup, returns `None` for unrecognized (no `PanicException`).
- Camelot stable + Aerodrome stable presets carry `gamma_numer=0` (no compile-time default — fees are per-pool on-chain) with the documented denominator. Aerodrome `init_hash` is `B256::ZERO` (Python source says "different address generation"; address derivation for Aerodrome is a separate path, deferred to a future slice).
