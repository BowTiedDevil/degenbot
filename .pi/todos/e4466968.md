Split the pump's `start()` into two phases:

1. **`subscribe(rpc_url, buffer_event_types)`** — opens WS connection, starts receiving block headers and logs. Returns the first observed block number so Python knows the temporal boundary for backfill. During this phase:
   - Events matching `buffer_event_types` (configurable, higher-level `EventType` enum, default: {MINT, BURN}) are buffered in the appropriate sub-engine
   - Swap/Sync events are discarded (stateless)
   - Buffer uses the same mechanism as the unregistered-pool Mint/Burn buffer

2. **`resume()`** — begins normal processing. The pump processes any buffered events from the subscribe phase, then continues with live event processing.

**Critical ordering guarantee**: Python must run backfill AFTER `subscribe()` returns (so it knows the current block) but BEFORE calling `resume()` (so the pump picks up from the right block with no gap). This ensures no blocks are missed.

**New startup sequence**:
1. Call `subscribe(ws_url)` immediately at startup
2. Observe first block from subscription → this is `backfill_to_block`
3. Run backfill to `backfill_to_block` (no gap)
4. Call `resume()` — pump begins processing from `backfill_to_block + 1`
5. Continue path loading in background
6. Main loop dispatches profitable results as paths come online

**Decisions**:
- `subscribe()` called immediately at startup, before any pool/path registration
- Configurable inclusion set using higher-level `EventType` enum (ergonomic)
- Default inclusion set: {MINT, BURN}
- Backfill target determined by subscription's first observed block
