## Problem

The `parking_lot::Mutex<UniswapEngine>` is held for the entire `solve_dirty` call including all `resolve_path` + `solve_path` work. For 100-200 affected paths, that's ~5-20ms of lock hold time where Python is blocked out. This matters because Python reads `latest_results()` under the same lock.

Location: `rust/src/optimizers/uniswap_engine.rs` (engine) + `rust/src/optimizers/uniswap_engine_pump.rs` (pump lock sites)

## Fix Options

1. **Compute results under the lock, then release before sending via channel** — the channel send is non-blocking (unbounded), so there's no reason to hold the lock during `compute_diff_and_send`.

2. **Split into read-lock (for pool state) and write-lock (for results)** — `resolve_path` reads pool state (write-lock freed after reading), `solve_path` is pure compute (no lock needed), results are written back under write-lock.

3. **Copy-on-write results** — `latest_results()` returns a clone of results under the lock, then Python processes the clone lock-free. This is already partially the case (Python reads results via the unbounded channel, not `latest_results`).

## Assessment

This is an architectural change. The current design is correct — the lock guards against concurrent mutation. The question is whether lock hold time is actually causing latency in practice. If Python's hot loop only reads from the unbounded channel (not `latest_results`), then lock contention is minimal. Worth measuring before committing to a refactor.
