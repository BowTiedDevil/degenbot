**Slice 3 of the Polars three-layer migration (ADR-005).** Master: `TODO-7e24d695`. Deps: none (first migration slice).

**Goal.** Make `Erc20Token` a Polars-style Python companion over `PyErc20Token`: Rust owns token metadata (address/symbol/name/decimals); Python keeps the price oracle (`ChainlinkPriceContract`) + display/subscriber concerns. This is the smallest companion migration (`PyErc20Token` already complete) and proves the companion pattern. Finally makes `Bot._py_bot` actually used.

**Rust (minimal).** `PyErc20Token` (`rust/src/bot_core/py_erc20_token.rs`) is already complete — no change expected. Confirm `TokenEntry` carries `chain_id` (it does, per `mod.rs`); add a `chain_id` getter to `PyErc20Token` only if the companion needs it. `PyBot.register_token`/`get_token` exist unchanged.

**Python class.** `Erc20Token` (`src/degenbot/erc20/erc20.py`): add `self._py_token: PyErc20Token` constructed via `self._py_bot.register_token(...)`; metadata property reads (`symbol`/`decimals`/`name`/`address`) delegate to `self._py_token`; price oracle + subscribers + `__init__` I/O stay Python. Must still satisfy `AbstractErc20Token` (address/symbol/name/decimals — unchanged surface).

**Builders.** `Erc20Builder` (`src/degenbot/builders/erc20_builder.py`): construct `PyErc20Token` via `PyBot.register_token(...)` → `get_token(...)`, then wrap with `Erc20Token`. `AsyncErc20Builder` mirrors. `Erc20Builder` keeps its standalone constructor (it's a leaf dependency used *by* `BuilderContext`).

**Registries.** `TokenRegistry` stores `Erc20Token` companions (over `PyErc20Token`).

**Bot session.** `Bot.build_erc20token` wires through `PyBot.register_token` → `PyErc20Token` → `Erc20Token`. Replaces the current pure-Python construction; `self._py_bot` finally delegated through.

**Tests.** Existing `Erc20Token` tests; `tests/test_bot.py` token-building tests; `tests/arbitrage/test_optimizers/test_py_bot.py` token-handle tests (TestTokenHandle). Add: metadata round-trip through `PyErc20Token`; builder→registry→`get_token` consistency.

**Consistency at boundary.** Token metadata reads return the same values (now sourced from Rust). Price-oracle lifecycle + subscribers unchanged. `Bot.build_erc20token` end-to-end green. Dual-state eliminated for token metadata (Rust is sole owner). `UniswapArbEngine` path unaffected (tokens aren't engine-managed state).

**Acceptance.** `cargo check`/`fmt --check`/`clippy --deny warnings`/`test`; `ruff check`/`ruff format --check`/`ty check` on `src/`; Erc20Token + `test_py_bot.py` token tests pass; import probe; `Bot.build_erc20token` round-trips metadata through `PyErc20Token`.

## REALIZED — Slice 3 complete (full-purge POC)

**Approach taken:** full (B) purge — `Erc20Token.__init__(py_token, *, oracle_address=..., state_cache_depth=...)`; `address`/`name`/`symbol`/`decimals`/`chain_id` became properties delegating to `self._py_token` (a `PyErc20Token` handle). `address` applies `get_checksum_address` on the Rust-sourced (lowercase) address to preserve the codebase-wide EIP-55 convention. `EtherPlaceholder` dropped its shadowing class-level `name`/`symbol`/`decimals` (metadata now registered in Rust when built). Price oracle + balance/approval/total-supply caches stay Python (I/O). `Erc20Builder`/`AsyncErc20Builder` take `py_bot: PyBot` and register via `PyBot.register_token` → wrap. `Bot`/`AsyncBot` wire `self._py_bot` through; `self._py_bot` is finally used. Added `chain_id` getter to `PyErc20Token` (Rust) — first core-struct addition beyond the rename slices.

## BLOW-UP FINDINGS (inform strategy for Slice 4 — per the user's POC framing)

1. **Construction pervasiveness undercounted ~2×.** Initial survey found ~40 direct `Erc20Token(...)` sites; the actual was ~70 across ~25 files (integration tests, conftests, fakes, optimizer tests — `test_solver_hop_builders` alone had 8 nested `token0=Erc20Token(...)`). All converted via a `sed` construction-swap (`s/\bErc20Token(/make_erc20(_PY_BOT, /g`) once imports were in place. **Strategy implication for Slice 4 (V2 pool companions):** V2 pools are constructed directly far more than tokens are; expect the same pattern at higher volume. Budget heavy mechanical churn OR invest in a transitional factory + `from_state(...)` classmethod that tests can adopt incrementally — the pure-purge-on-day-one approach is tractable but voluminous.

2. **Pickle incompatibility (real design consequence).** Pools pickle their tokens recursively (`PoolPickleMixin`); tokens now hold a non-picklable `PyErc20Token` (Rust `Arc<RwLock<Bot>>`). Fixed with `Erc20Token.__getstate__` (drops `_py_token`) — **unpickled tokens become detached snapshots** (no live Rust handle; metadata reads raise `AttributeError`). Acceptable because pool pickle persists the pool's OWN state (`StateCache`), not live token metadata, and nothing on the unpickled graph reads token metadata. **Strategy implication:** future pool-family slices (V2/V3/V4) face the same issue at the POOL level (a pool's `Py*` handle isn't picklable either) — `StateCache`/`PoolPickleMixin` already drop `_subscribers`; pools will need their `__getstate__` to drop the pool handle too. The detached-snapshot pattern is the template. (Alternative rejected: snapshotting metadata on pickle to keep detached tokens readable — would add a fallback path to every delegating property, partially re-approaching the stance-A shape the user rejected. Not done; flagged as future work.)

3. **Direct-builder-construction tests.** Tests that construct `AsyncErc20Builder`/`Erc20Builder` directly (not via `Bot`) needed the now-required `py_bot=` kwarg threaded in. **Strategy implication:** any builder gaining a required `_py_bot`/handle param will break its direct-construction tests the same way — budget for it.
