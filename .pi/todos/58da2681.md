## Resolution

All simulation reverts across all path types (V2/V3/V4) are caused by **one-block-old solver data**, NOT encoding bugs.

### Evidence

1. **V2-V2-V3**: `getAmountOut` comparison showed encoded amounts exceed current-reserve limits by 0.1% (stale K-invariant)
2. **V3-V3-V3**: `debug_traceCall` with injected executor code shows identical calldata SUCCEEDS against current pending state (reverts only with older pool state)
3. **V4-V3-V2**: All reverts are empty (`0x`) — no `CurrencyNotSettled` selectors
4. **V4-V3-V4**: 100% pass rate in fresh testing (was 15% in earlier test due to stale data during higher-volatility period)

### Root Cause

The solver uses engine state from block N, but `eth_simulateV1` simulates at "pending" (= state after block N). Any swap in block N that changes pool reserves/ticks/liquidity makes the solver's amounts stale. The `age=0` metric is misleading: `solve_block == current_block`, but the simulation target is always one block ahead of the engine's data.

### Fixes Applied

- **Pathfinding bug**: `_dfs`/`_dfs_async` `IndexError` when `pool_type_per_depth` has fewer entries than `max_depth` (e.g., `--permutation V2-V3`). Fixed by computing `effective_max_depth = min(max_depth, len(pool_type_per_depth))`.
- **V2 reserve diagnostic**: Added `getReserves()` fetch for V2 hops on empty-revert paths. Fixed `AttributeError` on `V4HopInfo` (no `pool_address`).
- **Sim logging**: Added `block=` and `age=` to `[sim-fail]` and `[sim-revert-data]` lines.
- **Test script**: Updated `test_all_permutations.sh` to decompose reverts into stale-vs-bug categories.
