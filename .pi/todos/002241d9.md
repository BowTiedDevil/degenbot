## Problem
The solver review flagged apparent "redundant topic filtering": the pump pre-filters logs by topic0 against `RELEVANT_TOPICS`, *and* `apply_log` re-matches topic0 internally. On reflection the pre-filter is **not** redundant — it skips acquiring `engine.lock()` (parking_lot mutex) and running decoders for the vast majority of irrelevant unfiltered-chain logs. But neither location explains *why* both checks exist, which invites a future cleanup that would regress lock-contention behavior.

## Evidence (verified)
- Pre-filter in `run_with_stream` log arm: `if !relevant_topic_set.contains(log.topics().first().unwrap_or(&B256::ZERO)) { continue; }` (`rust/src/optimizers/uniswap_engine_pump.rs`).
- Internal re-match in `apply_log`: `if *topic == V2_SYNC_TOPIC {...}` chain (`rust/src/optimizers/uniswap_engine/event_routing.rs:28+`).
- `filter_relevant_logs` (`uniswap_engine_pump.rs`) is the address-agnostic variant — its doc says engines handle unregistered addresses gracefully.

## Scope
- Add a short comment at the pump pre-filter explaining: it is a fast-path to avoid acquiring `engine.lock()` + running decoders for irrelevant logs, given the unfiltered `logs` WS subscription.
- Optionally note in `apply_log` that its topic re-check is intentional/defensive, so the method remains safe to call with unfiltered inputs.
- Verify `filter_relevant_logs` still has live call sites; if unused, flag a separate cleanup todo (do **not** delete here).
