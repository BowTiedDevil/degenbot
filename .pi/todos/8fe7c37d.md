## Symptom
V4-V3 paths 408 and 1092 sometimes sim-ok, sometimes sim-fail with CurrencyNotSettled (0x5212cba1). Both have `gross=0.000000ETH` (sub-gwei phantom profits, always negative net).

## Root Cause Hypothesis
Solver's predicted `forward_out` / `weth_out` slightly mismatches on-chain V3/V4 swap output due to pool state drift between solve block and simulate block. The V3 callback's `ERC20_TRANSFER(weth_idx, pm_idx, optimal_input)` transfers the exact V4 WETH debt, but if the V3 on-chain output differs from `weth_out`, the V4 settle may be short.

## Key Question
Is CurrencyNotSettled caused by:
1. WETH shortage: V3 actual output < optimal_input (executor can't cover V4 debt)?
2. Forward token mismatch: V4 actual output ≠ forward_out, so V3 gets wrong input → V3 output diverges?
3. Rounding: 1-wei differences in V3 CL math between solver and on-chain?

## Debugging Approach
- Log `optimal_input`, `forward_out`, `weth_out` for paths 408/1092 when they fail
- Compare solver's V4/V3 state vs on-chain `slot0`/`getReserves` at failure block
- Check if `V4_TAKE forward_out` over/under-pays the actual V4 output (causing V3 to get wrong input)

## Context
- V4-V3 encoder uses explicit forward_data: pay forward to V3, sync+transfer WETH (optimal_input) to PM, settle
- Verified pattern matches test_cmd_executor_v4v3.py::test_v4_v3_usdc_to_weth
- 15 sim-ok, 29 sim-fail on these 2 paths; all other V4-V3/4/2 encoders are clean
