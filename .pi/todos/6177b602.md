## Context

Surfaced during the Plan 100 completion audit. While reviewing whether the deferred `LiquidityMap` generic should have wrapped the per-pool scalar state, a sharper per-pool seam emerged that's currently carried by comments, not types.

The new `rust/CONTEXT.md` term **Slot0 Head / Tick Bookkeeping Map** names it: a single CL pool's state (`V3PoolState` / `V4PoolState`) is conceptually two parts with different mutation frequencies, different verification semantics, and different journal sub-structures — but today they're flat sibling `pub` fields on one struct.

| | Slot0 head | Tick bookkeeping map |
|---|---|---|
| fields | `sqrt_price_x96`, `tick`, active `liquidity` | `tick_data: HashMap<i32, TickInfo>` (gross/net per initialized tick) |
| mutation frequency | every Swap (+ `liquidity` at tick crossings inside the swap loop) | only Mint/Burn (V3) / `ModifyLiquidity` (V4) |
| verifier | explicitly **skipped** (module doc: "would always be stale") | the whole point of `verify_*_liquidity_map` |
| journal sub-structure | scalar priors in `V3BlockDelta` | per-tick priors in `V3BlockDelta` |

The seam already shows up operationally:
- `rust/src/bot_core/liquidity_verifier.rs` module doc draws exactly this line ("The liquidity map is the set of initialized ticks... Mutable scalar state like sqrtPriceX96, tick, and liquidity... is NOT verified here")
- `V3BlockDelta` carries them as separate sub-structures (scalar priors `Vec` + per-tick priors)
- `restore_before_block` reverse-applies them as two distinct steps (scalars, then tick priors)

## What this todo must decide

**Should the two halves become separate types?** Candidate shape:

```rust
pub struct V3PoolState {
    pub address: Address,
    pub token0: Address, pub token1: Address,
    pub fee: u32, pub tick_spacing: i32, pub factory: Address,
    pub coverage: PoolTickCoverage,
    pub slot0: Slot0Head,                    // high-churn scalars
    pub ticks: TickBookkeepingMap,            // low-churn tick_data + per-pool cache
    pub journal: ReorgJournal<V3BlockDelta>,
}
pub struct Slot0Head {
    pub sqrt_price_x96: U256,
    pub liquidity: u128,
    pub tick: i32,
    pub update_block: u64,
}
pub struct TickBookkeepingMap {
    pub tick_data: HashMap<i32, TickInfo>,
    cached_tick_ranges: parking_lot::Mutex<TickRangeCache>,
}
```

## The decision tree to walk (in order)

1. **Is there a real consumer that wants the boundary typed?** Survey every read site of `V3PoolState`/`V4PoolState` fields:
   - `v3_simulate_swap` / `v4_simulate_swap` — needs slot0 + ticks *in lockstep* per tick crossing (the strongest argument *against* a split — they're one deep module)
   - `verify_v3_pool` / `verify_v4_pool` — wants *only* the tick map
   - `restore_before_block` (V3/V4) — operates on both halves as two steps
   - `diagnostic_pool_state` (V4 variant) — reads both
   - `build_int_v3_sequence` / `build_int_v4_sequence` — reads slot0 + ticks together (via the cached ranges)
   - `apply_v3_swap` / `apply_v4_swap` — writes slot0 (+ tick priors if provided)
   - `apply_v3_liquidity_update` / `apply_v4_liquidity_update` — writes *only* the tick map

   The split only earns its keep if a caller wants *one half alone* and the flat layout forces it to take the whole pool + recover the rule from a comment. If every caller actually wants both (or the cost of "taking the whole pool" is trivial), the split is pure layering.

2. **Does the split deepen or shallow the module?** Per the improve-codebase-architecture "depth" vocabulary: a deep module has a small interface hiding a large implementation. The question is whether `v3_simulate_swap`'s lockstep reads make V3PoolState one deep module, or whether the verification/restore callers reveal that there are *two* deep modules hiding behind one flat struct.

3. **Does a split pay for itself on verification specifically?** The strongest concrete case today: `verify_*_liquidity_map` takes `&V3PoolState` and relies on a doc comment to enforce "don't read slot0." If it took `&TickBookkeepingMap` the type would carry the rule. Is that worth the cost of `v3_simulate_swap` having to reach through `state.slot0.sqrt_price_x96` + `state.ticks.tick_data` instead of flat field access? (Probably yes for clarity, probably no for the hot loop — needs a measured view.)

4. **Does the journal already encode the answer?** `V3BlockDelta` bundles both halves as sub-structures. Is that a leading indicator (the journal "knew" they were two things) or a coincidental packing (the delta is per-block-per-pool regardless of internal structure)?

5. **V4 parity.** Whatever is decided must apply identically to V4 — both CL families share the `V3BlockDelta` shape and the `v3_simulate_swap`/`v4_simulate_swap` structure. A split should land in `bot_core::v3_state` and `bot_core::v4_state` symmetrically, or not at all.
