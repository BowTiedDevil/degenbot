## Context

Surfaced during the Plan 100 completion audit. While reviewing whether the deferred `LiquidityMap` generic should have wrapped the per-pool scalar state, a sharper per-pool seam emerged that's currently carried by comments, not types.

The `rust/CONTEXT.md` term **Slot0 Head / Tick Bookkeeping Map** names it: a single CL pool's state (`V3PoolState` / `V4PoolState`) is conceptually two parts with different mutation frequencies, different verification semantics, and different journal sub-structures — but today they're flat sibling `pub` fields on one struct.

| | Slot0 head | Tick bookkeeping map |
|---|---|---|
| fields | `sqrt_price_x96`, `tick`, active `liquidity` | `tick_data: HashMap<i32, TickInfo>` (gross/net per initialized tick) |
| mutation frequency | every Swap (+ `liquidity` at tick crossings inside the swap loop) | only Mint/Burn (V3) / `ModifyLiquidity` (V4) |
| verifier | explicitly **skipped** (module doc: "would always be stale") | the whole point of `verify_*_liquidity_map` |
| journal sub-structure | scalar priors in `V3BlockDelta` | per-tick priors in `V3BlockDelta` |

The seam already shows up operationally:
- `rust/src/bot_core/liquidity_verifier.rs` module doc draws exactly this line ("The liquidity map is the set of initialized ticks... Mutable scalar state like sqrtPriceX96, tick, and liquidity... is NOT verified here")
- `V3BlockDelta` carries them as separate sub-structures (scalar priors `Vec` + per-tick priors)
- `restore_before_block` reverse-applies them as two distinct steps (scalars, then tick priors)

## Reframing (read first)

This work defines the **Rust target architecture** the post-Python migration will land into. Python is **prior art for study** — inspected already, cited in the ADR's prior-art section, and **never** classified in the per-`file:line` survey table.

## Python prior-art findings (already inspected)

Studied `src/degenbot/uniswap/v3_liquidity_pool.py` + `concentrated/liquidity_map.py` + `concentrated/state_manager.py` + `v3_pool_state.py`. Findings:

- **Python did NOT solve the seam by splitting its state struct.** `UniswapV3PoolState` (built via `__value__`) carries `liquidity, sqrt_price_x96, tick, tick_bitmap, tick_data, block` as flat sibling fields — identical to Rust's flat layout.
- **But the tick half IS its own type in Python.** `LiquidityMapSnapshot` (`concentrated/liquidity_map.py`, frozen/slots dataclass: `tick_data, tick_bitmap, tick_spacing, sparse`), duck-typed for V3 *and* V4 via `_HasTickData` / `_HasPoolLiquidityMap` protocols, with behavior (`next_initialized_tick`, `ticks_along_path`, `from_pool`, `from_state`).
- **The simulation seam consumes the two halves separately.** `_v3_swap(snapshot: LiquidityMapSnapshot, *, liquidity_start, sqrt_price_x96_start, tick_start, …)` takes the tick half as a *typed snapshot* and the scalars as *separate args* — it does **not** take the whole pool state. This is the hottest consumer the Rust decision tree feared would force a whole-pool signature — and Python shows it doesn't.
- **Mutation paths split at the method level via `dataclasses.replace`:** `external_update()` → slot0 scalars; `update_liquidity_map()` / `update_tick_data()` → tick map (tick_data, tick_bitmap, + in-range liquidity adj).
- **Temporal navigation is orthogonal.** `ConcentratedLiquidityStateManager[StateT: _StateLike]` treats the state as opaque and only does deque/lock/discard/restore — it mirrors Rust's `ReorgJournal<V3BlockDelta>` concern and doesn't care about the slot0/ticks split.

**Implication for the recorded CONTEXT.md hold reason.** The hold reason states: *"`v3_simulate_swap` reads slot0 + tick_data in lockstep at every tick crossing, so they are one *deep* module, not two shallow ones."* This is **partially undercut** by the Python precedent: Python's `_v3_swap` *also* reads them in lockstep, yet does so through a typed snapshot + scalar args, and it ships. The "deep module" argument cuts against one *flat-struct* reading — it does **not** cut against a *tick-half-as-typed-snapshot* split. The survey must decide which reading wins.

## The three outcomes (all genuinely open per Q3/Q4)

- **(A) Full split.** `V3PoolState` / `V4PoolState` gain `slot0: Slot0Head` + `ticks: TickBookkeepingMap` sub-structs; every read/write site migrated; journal shape aligned.
- **(B) Trait-only on the verifier seam.** State structs stay flat; `verify_*_liquidity_map` (and restore, if the survey says) take a trait/view object that exposes only the tick half. The type — not a doc comment — carries the "don't read slot0" rule.
- **(C) Hold.** No structural change. The `rust/CONTEXT.md` "held as non-structural" ruling is **strengthened** from a deferral to a firm decision, with the survey evidence as the reason (e.g., "no `ticks-only` consumer surfaced; the CONTEXT.md deep-module reasoning holds").

The survey, not this todo, picks among them.

## Reasoned analysis (replaces benchmarking — per Q5)

No criterion benches stand up. The ADR's "does the split hurt the hot loop?" argument is reasoned from first principles:
- One extra field indirection per accessor (`state.slot0.sqrt_price_x96` instead of `state.sqrt_price_x96`) is dominated by the per-tick-crossing math.
- The simulator already pays a method-call boundary; the indirection is not a new cost category.
- `IntHopState` / `PyPoolCache` pre-convert slot0 fields to `U512` at construction, so the inner solve loop does not dereference through the state struct at all.
- Python's `_v3_swap` already runs the tick-crossing loop through a typed snapshot + scalar args in production — a working existence proof that the split shape doesn't fatally cost the hot loop.

Record the argument in the ADR; commit the ruling on survey + reasoning. Benches only if reasoning is later shown wrong by a regression.

## Structural findings the survey surfaced (these are themselves deliverables)

### Finding S1 — `LiquidityMap` generic does NOT exist in code; the {LiquidityMap} and {PyBotCore} CONTEXT.md terms are stale

`rg -n 'struct LiquidityMap|impl.*LiquidityMap|LiquidityMap<' src/` returns nothing. ADR-003 and the {BotCore} term both say: *"The standalone `LiquidityMap` generic was NOT extracted: the inline-`PoolEntry` + `BotCore::apply_*` pattern suited V2/V3/V4."* But `{LiquidityMap}` (CONTEXT.md) and `{PyBotCore}` still describe generic `LiquidityMap<V3PoolState>`/`LiquidityMap<V4PoolState>` types and a `LiquidityMap::verify_against_onchain` method as if they exist. **The reality is flat:** `BotCore` holds `pools: HashMap<u64, PoolEntry>` where `PoolEntry::V3(V3PoolState)` / `PoolEntry::V4(V4PoolState)`, and verification is the free functions `verify_v3_pool`/`verify_v4_pool`/`verify_v3_liquidity_map`/`verify_v4_liquidity_map` in `liquidity_verifier.rs`. The survey-classification table uses the real free-function names.

**Action for Slice 1/2:** the {LiquidityMap} and {PyBotCore} CONTEXT.md terms must be corrected in the same doc pass as the {Slot0 Head} term flip. (Slice 1 already touches `rust/CONTEXT.md`; add these two stale-term fixes to its scope.)

### Finding S2 — `PyPoolCache` and `RustPoolCache` do NOT exist; the {PyPoolCache} term is stale, and the optimizer-cache question is already resolved

Exhaustive `rg -n 'PyPoolCache|pool_cache|RustPoolCache|LruCache<u64|LruCache<.*IntHop|cache_get|cache_insert' src/` exits code 1 (zero matches). ADR-003 "Legacy solver path retirement: delete, not migrate" explicitly records this deletion: *"`Rust: RustPoolCache, RustIntHopState, RustArbResult PyO3 classes deleted from mobius_py.rs."* The CONTEXT.md {PyPoolCache} and {IntHopState} terms still describe a `parking_lot::Mutex<LruCache<u64, IntHopState>>` bounded LRU keyed by pool ID — that object is gone.

**The optimizer-cache finding (the Q6-question the survey was told to answer as output, not presupposition):**

- **What survives as memoization is the per-pool `cached_tick_ranges: parking_lot::Mutex<TickRangeCache>` field on `V3PoolState`/`V4PoolState`.** It caches the `compute_tick_ranges` output per direction, invalidated on every `apply_*`. The live solve path (`solver_dispatch.rs:336, 348`) calls `pool_state.build_int_v3_sequence(zfo, 10)` / `build_int_v4_sequence(zfo, 10)`, which reads that per-pool cache and never builds a cross-pool LRU.
- `IntHopState` survives as a *struct* (`src/optimizers/mobius_int.rs:96`) but is constructed only in *tests* (`mobius_int_exact.rs`) and consumed by `exact_mobius_solve` for V2; the live V3/V4 solve path does not pass `IntHopState` to the solver — it passes `IntV3TickRangeSequence`, built fresh per solve by `build_int_v3_sequence`.
- **Recommendation (carries to ADR-004 consequences):** the {PyPoolCache} term must be removed from `rust/CONTEXT.md` (or rewritten to name what was removed, matching the {Dual-Orientation Registration} / {V2Snapshot} removed-term pattern). The {IntHopState} term stays but its description must drop the "stored in `PyPoolCache`" framing and say "constructed by `build_int_v3_sequence` per solve; cached per-pool via `V3PoolState.cached_tick_ranges`." The per-pool `cached_tick_ranges` derivation cache **survives** into the migrated design as-is — it is the actual memoization seam, and any split candidate (S2+) must keep it attached to whichever half owns `tick_data` + `liquidity` (it reads both).

**Direct consequence for the todo body's reasoned-analysis section:** the argument *"IntHopState / PyPoolCache pre-convert slot0 fields to U512 at construction, so the inner solve loop does not dereference through the state struct"* is anchored to deleted code. **The real argument is:** `build_int_v3_sequence` runs once per `solve_dirty` (per dirty-path burst, coalesced) and produces `IntV3TickRangeSequence`; the V3/V4 Mobius solver (`mobius_v3_int.rs`) operates on `IntV3TickRangeHop` fields, never on `V3PoolState`. The per-tick-crossing inner loop in the *solver* does not dereference the state struct; the *simulator* (`v3_simulate_swap`) does, but `v3_simulate_swap` is the single-pool-query path (`calculate_tokens_out`/`calculate_tokens_in`), not the solver hot loop. Slice 1 must re-anchor the ADR's reasoned analysis to this real mechanism.

### Finding S3 — the two verifier entry points already diverge; the typed boundary has a working precedent in the same file

- `verify_v3_liquidity_map` (`liquidity_verifier.rs:103`) and `verify_v4_liquidity_map` (`:136`) — the **snapshot-block** variants — already take `&HashMap<i32, TickInfo, S>` + `pool_address: Address` + `block_number: u64`. They take the **tick map as a typed arg** and do NOT take `&V3PoolState` at all. This is candidate trait shape (β) already shipping, for the snapshot-block verification path.
- `verify_v3_pool` (`:187`) and `verify_v4_pool` (`:410`) — the **live** variants — take `&V3PoolState` / `&V4PoolState` and read `pool.address` (immutable), `pool.tick_spacing` (immutable), `pool.tick` (**a slot0 scalar**), `pool.tick_data` (ticks). The slot0 read of `pool.tick` is purely to seed the ±2 word scan around the current tick during bitmap discovery — it is **not** verification content. The module doc explicitly carries the rule in prose: *"mutable scalar state like sqrtPriceX96, tick, and liquidity changes on every swap and is NOT verified here."* This is exactly the {Slot0 Head / Tick Bookkeeping Map} CONTEXT.md trigger condition: "the first caller that needs to verify or restore *only* the map … and resents passing the whole pool + recovering the rule from a comment." A typed boundary for these two functions pays for itself today, with the implementation shape already demonstrated 200 lines above in the same file.

### Counts
- **`both`** (genuinely wants both halves): 8 sites (#1, #2, #3, #4, #11, #12, #14, #15, #16, #18, #19, #20, #21 — counting function-level, that's 12 rows; #19 is the accessor)
- **`ticks-only`** (no slot0 read at all): 3 sites (#5, #6, #22-`debug_v3_tick_data`)
- **`takes-whole-but-wants-one`** (the seam-paying signal): 6 sites (#7, #8, #9, #10, #13, #17, #22-`verify_v3_pool`, #22-`verify_v4_pool`)
- **`slot0-only`**: 0 sites — no consumer reads *only* the slot0 head and never the tick map. (Confirms: the slot0 head is never read in isolation; the closest is `v3_simulate_swap` reading slot0 + ticks in lockstep, which is `both`.)

### Synthesis of the four-way result
1. **A paying, named consumer exists:** the four `verify_*_pool` sites (#7–#10) plus the two liquidity-update apply sites (#13, #17) are `takes-whole-but-wants-one` — six sites that want only the tick map and recover the "don't read slot0" rule from comments or from the journal's forcing shape. The CONTEXT.md deferral trigger condition is met.
2. **A working typed-boundary precedent exists** in the same file as the offending sites: `verify_v3_liquidity_map` / `verify_v4_liquidity_map` already take `&HashMap<i32, TickInfo>` + `Address` + block. Candidate (β) is not hypothetical — it's already shipping for the snapshot-block case; the live case was simply never converted.
3. **No `slot0-only` consumer exists** anywhere. The slot0 head is *never* read in isolation. This is the single most decisive fact for the ruling: splitting `Slot0Head` out as its own type earns nothing, because nothing reads it without also reading ticks. The paying boundary is one-directional — it lives entirely on the tick side. Candidate (α) full-split of `Slot0Head` is therefore pure layering; candidate (β) typed-tick-view is the minimal move that captures all six paying sites.

## Candidate trait shapes (evaluated — paying consumers surfaced)

### (α) snapshot-per-call — a `LiquidityMapSnapshot`-style frozen value threaded into `v3_simulate_swap` / `v4_simulate_swap`

- **Shape** (mirrors Python's `_v3_swap`): `v3_simulate_swap(snapshot: &TickBookkeepingMap, slot0: &Slot0Head, immutables: &PoolImmutables, zero_for_one, amount_specified) -> Option<V3SwapOutcome>`.
- **Sites satisfied:** #2, #4, #20 (the simulator-call sites). Also aligns #1, #3 if `build_int_v3_sequence` is refactored to take `(snapshot, slot0)` instead of `&self`.
- **Sites NOT satisfied:** the six `takes-whole-but-wants-one` verifier/liquidity-update sites (#7–#10, #13, #17) do NOT want a snapshot — they want to read the live tick map, not a frozen one. A snapshot is the wrong shape for them (it copies; the verifier needs live references for RPC comparison, and the apply path mutates).
- **Migration cost:** HIGH. The simulator is the *lockstep* consumer — splitting its signature is exactly the move the CONTEXT.md hold reason feared. Even with reasoned-analysis clearing the performance question, it forces every `v3_simulate_swap`/`v4_simulate_swap`/`build_int_v3_sequence`/`build_int_v4_sequence`/`calculate_tokens_out`/`calculate_tokens_in` call site to thread 3 args instead of 1, for zero semantic gain (these sites genuinely want both halves).
- **Verdict:** does NOT pay for itself. It splits the lockstep consumers (which want both halves anyway) into a more verbose signature, while failing to address the six `takes-whole-but-wants-one` sites that actually pay. **Rejected.**

### (β) protocol view — a typed view trait that `verify_*_pool` (and the live variant of `verify_v3_liquidity_map`) take instead of `&V3PoolState` / `&V4PoolState`

- **Shape:**
  ```rust
  pub trait TickMap {
      fn address(&self) -> Address;          // immutable, needed for RPC target
      fn tick_spacing(&self) -> i32;        // immutable, needed for bitmap word compression
      fn active_tick(&self) -> i32;          // slot0 scalar, read-only, for ±2 word scan
      fn tick_data(&self) -> &HashMap<i32, TickInfo>;
  }
  impl TickMap for V3PoolState { ... }       // blanket over the existing fields
  impl TickMap for V4PoolState { ... }
  ```
  Then `verify_v3_pool(provider: &AlloyProvider, pool: &impl TickMap, ...)` — the type carries the "verify ticks, do NOT read slot0 scalars (sqrt/liquidity)" rule. Python's `_HasTickData` duck-type made the same move.
- **Sites satisfied (all six paying ones):** #7, #8, #9, #10 (verifier — direct conversion), #13, #17 (liquidity-update apply — these want `&mut TickMap`, slightly different trait `TickMapMut` exposing `tick_data_mut`, but same shape). The apply sites' "journal slot0 unchanged" artifact (S3) is **exposed as a real wart** by this conversion: trait `TickMap` has no `set_sqrt_price`/`set_liquidity`/`set_tick` — so the apply path can no longer "accidentally" journal slot0 priors it didn't change. The `V3BlockDelta` shape must either gain a "scalars-unchanged" flag or split into `ScalarDelta` + `TickMapDelta` — which is a real, but contained, journal refactor.
- **Sites NOT satisfied:** the `both` consumers (#1, #2, #3, #4, #11, #12, #14, #15, #16, #18, #19, #20, #21) are untouched — they keep taking `&V3PoolState`/`&V4PoolState`, exactly as Python's `_v3_swap` + simulator kept the flat state.
- **Migration cost:** LOW-MEDIUM. 6 function signatures change (+ the live variant of `verify_v3_liquidity_map` could be merged onto the trait). One new trait + two `impl` blocks. The `V3BlockDelta` shape must be revisited to express "scalars unchanged" cleanly (the apply-liquidity case) — the cleanest resolution is to make scalar priors `Option<ScalarPriors>` in `V3BlockDelta` (None when unchanged), which also reduces journal storage for Mint/Burn/`ModifyLiquidity` (currently stores slot0 priors redundantly).
- **Verdict:** pays for itself cleanly. Captures all six paying sites by name, uses a shape Python already proved, leaves the lockstep `both` consumers untouched, and surfaces a latent journal wart (redundant slot0 priors on tick-only events) as a fix. **This is the recommended ruling.**

### (γ) hold — strengthen the {Slot0 Head} term to a firm ruling; no code change

- **Stance:** the survey found a paying consumer, so the CONTEXT.md hold reason ("deep module, not two shallow ones") is empirically refuted for the *typed-boundary* reading (candidate β pays). Holding is therefore not the neutral default — it's now a positive decision to leave six `takes-whole-but-wants-one` sites recovering the rule from comments, when a 1-trait fix exists with a shipping precedent.
- **Only justified if:** the journal-shape complication (the `Option<ScalarPriors>` refactor of `V3BlockDelta`) is judged too risky for the per-pool seam before the migration. Argument against: that refactor is independently desirable (it shrinks Mint/Burn/`ModifyLiquidity` journals — currently redundant slot0 priors), and it's contained to `state_history.rs`.
- **Verdict:** defensible but not the survey's recommendation. Listed as the fallback if a Slice-2 implementation review finds the `V3BlockDelta` refactor spills beyond `state_history.rs`.

## Ruling recommendation

**`trait-only` (candidate β).**

Evidence cited:
1. Six `takes-whole-but-wants-one` sites (#7, #8, #9, #10, #13, #17) — the CONTEXT.md deferral trigger condition is unambiguously met; the rule is recovered from comments today.
2. A working typed-boundary precedent already ships 200 lines above the offending sites (`verify_v3_liquidity_map` / `verify_v4_liquidity_map` take `&HashMap<i32, TickInfo>` + `Address` + block) — candidate β is not new architecture, it's completing a conversion that was started and paused.
3. Zero `slot0-only` consumers exist — candidate (α) full-split of `Slot0Head` earns nothing and pays a HIGH migration cost at the lockstep simulator sites that genuinely want both halves. The full-split candidate is rejected by the survey evidence, not by the hold reason.
4. The {Pool's authority over its own math} principle is preserved — `v3_simulate_swap` / `v4_simulate_swap` / `build_int_v3_sequence` / `build_int_v*_sequence` keep reading the whole state by reference; the trait only narrows the verifier + liquidity-update apply views.
5. V4 parity is trivial — the same `TickMap` trait blankets both `V3PoolState` and `V4PoolState`; #9/#10/#17 mirror #7/#8/#13 line-for-line.
6. Surfaces a latent journal wart (V3BlockDelta stores redundant slot0 priors on tick-only Mint/Burn/`ModifyLiquidity` events) as a contained fix in `state_history.rs`, payable independently of the seam decision.

**The full-split candidate (A) is rejected by survey evidence** — it's pure layering at the lockstep sites and offers no paying consumer (zero `slot0-only` readers). Recorded as an Alternative in ADR-004 with this evidence.

**The hold candidate (C) is demoted to a fallback** — the survey found a paying consumer and a shipping precedent, so holding is no longer neutral; it's a positive decision to keep the rule in comments. Recorded as an Alternative with the "if the V3BlockDelta refactor spills, revisit" caveat.
