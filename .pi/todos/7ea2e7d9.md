**Pre-existing bug surfaced by ADR-005 slice 7 step 4a** (the Camelot stable-strategy fold). NOT caused by the fold — the fold preserves the bug faithfully.

`calc_exact_in_stable` (src/degenbot/calculations/solidly_stable.py:~110) calls `get_y_func(x, xy, y, decimals0, decimals1)` — **5 args**. But `get_y_camelot` (src/degenbot/calculations/camelot.py:53) takes **3 args** (`x_0, xy, y`). So passing `get_y_func=get_y_camelot` to `calc_exact_in_stable` raises `TypeError` for every input.

**Impact:** Camelot's stable `to_hop_state` branch (dead code; always raises `TypeError`). The SOLIDLY (Aerodrome) path is unaffected — Aerodrome's `get_y` takes the 5-arg form. The direct stable CALC path (`_calculate_tokens_out_from_tokens_in_stable_swap`, folded into `LiquidityPool` in step 4a) is also unaffected — it calls `k_camelot`/`get_y_camelot` DIRECTLY with the right arity, bypassing `calc_exact_in_stable`.

**Root cause:** Incomplete refactor — `calc_exact_in_stable` was changed to invoke `get_y_func` with `(x, xy, y, decimals0, decimals1)` (for Aerodrome's `get_y`, which needs decimals for scaling), but `get_y_camelot` was never adapted to the 5-arg signature (Camelot's Newton loop doesn't need decimals — it uses `solidly_calc_d` internally).

**Fix options:**
1. Wrap `get_y_camelot` in a 5-arg adapter that drops the decimals: `lambda x, xy, y, _d0, _d1: get_y_camelot(x, xy, y)`. Minimal, localized.
2. Give `get_y_camelot` optional `decimals0`/`decimals1` params it ignores (signature aligns with the 5-arg contract).
3. Make `calc_exact_in_stable`'s `get_y` calling convention variadic/protocol-based.

**Where the bug lives now (post-4a):** the dead stable `to_hop_state` branch is duplicated — in `src/degenbot/camelot/pools.py:CamelotLiquidityPool.to_hop_state` (deleted in step 4b) AND the folded copy in `src/degenbot/uniswap/liquidity_pool.py:LiquidityPool.to_hop_state` (survives 4b). When 4b deletes `CamelotLiquidityPool`, the folded (still-broken) copy in `LiquidityPool` is the only one. This fix should target the folded copy.

**Verification when fixed:** the transitional parity test `tests/uniswap/v2/test_liquidity_pool_camelot_fold.py::TestFoldedToHopState::test_stable_to_hop_state_swap_fn_matches_reference` currently asserts "both raise the same exception" (workaround for the bug). After fixing, it should assert value parity instead. The `TODO: fix get_y_camelot↔calc_exact_in_stable arity` comment in that test + in `liquidity_pool.py` points here.

**Priority:** low (dead code; no passing test exercises the stable hop). But worth fixing before anyone relies on Camelot stable arbitrage hops.
