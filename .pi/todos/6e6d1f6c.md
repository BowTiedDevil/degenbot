## Problem
The backfill/pump dual-buffer pattern lives twice — once in V3BlockEngine, once in V4BlockEngine, with identical method signatures and expiry logic. The only difference is the key type and the liquidity-delta signedness.

## Files
- `rust/src/optimizers/v3_block_engine.rs` — `backfill_event_buffer: HashMap<Address, Vec<BufferedV3LiquidityUpdate>>` + `pump_event_buffer: HashMap<Address, Vec<BufferedV3LiquidityUpdate>>`
- `rust/src/optimizers/v4_block_engine.rs` — `backfill_event_buffer: HashMap<(Address, PoolId), Vec<BufferedV4LiquidityUpdate>>` + `pump_event_buffer: HashMap<(Address, PoolId), Vec<BufferedV4LiquidityUpdate>>`

Identical methods duplicated in both:
- `buffer_backfill_liquidity_update()` — route to backfill buffer, apply directly if pool exists
- `apply_backfill_buffer()` — drain and apply backfill events for one pool
- `apply_pump_buffer()` — drain and apply pump events for one pool
- `set_event_buffer_max_age()` — configure max age
- `buffered_event_count()` — count for a key
- `flush_event_buffer()` — clear all
- `expire_buffered_events()` — evict stale pump events

## Design
Extract a `LiquidityEventBuffer<K, Update>` struct that owns both HashMaps and implements the full buffer lifecycle.

### Struct definition
```rust
struct LiquidityEventBuffer<K, Update>
where
    K: Eq + Hash + Clone,
{
    backfill: HashMap<K, Vec<Update>>,
    pump: HashMap<K, Vec<Update>>,
    max_age: Option<u64>,
}
```

### Methods
- `buffer_backfill(&mut self, key: K, update: Update)`
- `apply_backfill_buffer(&mut self, key: &K) -> Vec<Update>` (returns drained events; caller applies them)
- `apply_pump_buffer(&mut self, key: &K) -> Vec<Update>` (returns drained events; caller applies them)
- `set_max_age(&mut self, max_age: Option<u64>)`
- `event_count(&self, key: &K) -> usize`
- `flush(&mut self)`
- `expire(&mut self, current_block: u64)` — only expires pump buffer; backfill is never expired

### Key design decision: who applies the updates?
The buffer should NOT apply updates to pool state — that's the engine's responsibility (it needs to call `update_tick_liquidity` and invalidate the cache). The buffer drains and returns the updates; the engine applies them.

This means `apply_backfill_buffer` and `apply_pump_buffer` on the engine become:
```rust
fn apply_backfill_buffer(&mut self, key: &K) {
    let updates = self.buffer.apply_backfill_buffer(key);
    for update in updates {
        // engine-specific application: update_tick_liquidity, cache invalidation
    }
}
```

### Delta type accommodation
V3 uses `i128` (from Mint/Burn events). V4 uses `I256` (from ModifyLiquidity). The `Update` generic must carry the delta. Two options:
1. **Separate update types**: `BufferedV3LiquidityUpdate` with `liquidity_delta: i128`, `BufferedV4LiquidityUpdate` with `liquidity_delta: I256` — each carrying `tick_lower`, `tick_upper`, `block_number`
2. **Generic delta**: `BufferedLiquidityUpdate<D>` where `D: Copy` — `D = i128` for V3, `D = I256` for V4

Option 2 is cleaner and matches the existing struct shapes.

### Integration with Candidate #1
If Candidate #1 (`CLBlockEngine<PoolId>`) is done first, this extraction becomes trivial — V3 and V4 already share the same engine, and the buffer is just one field instead of two.
