The solve seam is blind to the liquidity clock

Strong in-process

Files

  • pools/v3_state.rs · v4_state.rs (build_int_v*_sequence)
  • solvers/mixed/mod.rs (ResolvedMixedPath :: max_update_block)
  • solvers/mixed/solve.rs
  • bot/solver_state_verifier.rs (ADR-021 anchor diff)

Vocabulary

The solve seam (ADR-015 intake) stamps only the price clock (max_update_block). The liquidity clock — tick_data_block, the clock the solver's own int-V3 sequence is built from — never crosses the seam.

Problem — the solver consumes a tick map whose freshness it cannot see

The two-stamp design (OB7UNY) lets a CL pool carry a fresh price but a stale liquidity map — by construction: a fresh-read builder seeds update_block at the HEAD slot0 read while tick_data_block stays at the DB snapshot block (v4_state.rs:167–173). The solver builds IntV3TickRangeSequence from that tick map, but the intake only carries the price-clock nonce, so the solve seam cannot express "the map I solved on is stale." The 0x5653 staged-clock class is documented as "the scalar-only ADR-021 anchor diff cannot see." Deletion test: drop the two-stamp and the staleness knowledge re-concentrates across every CL consumer — it wants a home at the seam.

After — liquidity clock crosses the seam; one stance

flowchart LR

  P -->|liquidity clock| I
  I --> D{map fresher than price?}
  D -->|no / within tolerance| SOL[solve]

Solution

Add a per-hop liquidity clock (tick_data_block) to the ADR-015 intake next to max_update_block, and give the dispatch seam a single stance on price-fresh-but-map-stale: either refuse to solve a path whose map lags its price, or refresh the map before solving. One discriminator, one stop or one repair — never a silent mixed-clock solve.

  • Locality — the 0x5653 class stops being a hand-decoded log artifact; it is a typed verdict at the seam.
  • Leverage — the ADR-021 anchor diff, the future-price guard, and the stale-map guard all read clocks from one intake.
  • Testability — a seeded fresh-price/stale-map pool is a pure unit case at the dispatch seam; no chain access.

ADR alignment — extends ADR-015 + ADR-021; contradicts none.

ADR-015 fixes the seam's composition; this adds the missing clock to its intake. ADR-021 is fail-fast stop-only — a refresh stance would need new posture (offer it only as an explicit option, defaulting to refuse). No settled decision is re-opened.

State-accuracy events have no typed home — reproduction is string-coupled

Strong in-process · local-substitutable

Files

  • 21 Rust emit sites (sim-revert-swap / solver-st / sim-diag / sim-fail)
  • 7 Python regex parsers (watch_fee1_overdraw.py, dump_pool_state.py, …)
  • bespoke per-recurrence: capture_*.py + *_fixture.rs + 8 JSON fixtures

Vocabulary

The engine's state-accuracy event is a log string, not a value. The seam between "engine observes an over-prediction" and "tooling replays it" has no adapter — Python regex-parses the very literals 21 Rust files emit.

Problem — every recurrence buys a new script, not a reusable pull

An over-prediction is observed by emitting [sim-revert-swap] … predicted=… actual=…, then a Python watcher regex-parses that exact string out of logs/bot_run.log, then a bespoke capture_*.py rebuilds the block, then a hand-wired *_solver_fixture.rs + JSON fixture replay it. The event's shape lives in a string literal; the toolchain's contract is the literal spelling. Three recurrences have produced three capture scripts, three fixtures and three harness examples. This is a shallow seam — the "event → reproduction pull" knowledge is not concentrated, so each recurrence re-derives it across two languages.

Before — log string is the contract

  L -->|regex parse| W[watch_fee1_overdraw.py]
  L -->|regex parse| D[dump_pool_state.py]
  W --> C1[capture_fee1 script]
  C1 --> F1[fee1 fixture + harness]
  D --> C2[capture_path11354 script]
  C2 --> F2[11354 fixture + harness]

After — one probe-event module, one replay pull

flowchart LR
  E[engine] -->|typed event| P[probe-event module]
  P --> R[recurrence-replay seam]
  R -->|fixture + harness| H[one solver-fixture runner]
  R -->|live watch adapter| W[watch tool]
  classDef dp2 fill:#0f172a,color:#fff;
  class P dp2

Solution

Emit state-accuracy events as a typed payload behind one probe module (one emitter, one writer — the log line becomes a rendering of the value, not the value), and give reproduction a single seam: one fixture builder + one solver-fixture runner parameterised by the event, with the Python watch tool as a thin adapter over the typed output. A new recurrence stops meaning "write a new script and harness."

  • Locality — event shape lives once; 7 regex parsers and 21 emit sites collapse behind one module.
  • Leverage — the reproduction pull is reused for every future recurrence instead of re-derived.
  • Testability — a typed event is assertable directly; no log-mine to prove the probe saw it.

The pure solve result carries a String diagnostic channel

Worth exploring in-process

Files

  • solvers/mixed/mod.rs (SolvePathResult :: solver_pool_states: Vec<String>)
  • solvers/mixed/solve.rs
  • bot/solvers/arb_engine/solver_dispatch.rs (.join(";"))

Vocabulary

A shallow widening: SolvePathResult — the pure-solve result type — grew a Vec<String> payload whose only consumer joins it back into a [sim-diag] log line.

Problem — pre-formatted strings cross the pure-solve seam

SolvePathResult.solver_pool_states holds hop-family-specific display strings ("V3:sq=…,liq=…,fee=…,zfo=…") populated by solve_path and re-joined by solver_dispatch.rs into a [sim-diag] line. The pure solve layer (ADR-015's "value-only solver math") now formats diagnostic strings — a concern it shouldn't own, and a widening of its interface just to feed the log toolchain. The interface is as wide as the implementation it hides.

Before — strings in the value

flowchart LR
  SOL[solve_path] -->|"hop_outputs, consumed_inputs, + Vec<String>"| R[SolvePathResult]
  R -->|join(';')| LOG[[sim-diag log]]
  classDef l3 stroke:#dc2626,stroke-width:2px;
  class R,LOG l3

After — typed per-hop state in the value

flowchart LR
  SOL[solve_path] -->|"hop_outputs, consumed_inputs, per-hop scalar state"| R2[SolvePathResult]
  R2 --> FMT[render at the seam]
  FMT --> LOG2[[sim-diag log]]
  classDef dp3 fill:#0f172a,color:#fff;
  class R2 dp3

Solution

Return the per-hop scalar state the solver already holds as typed values in the result, and move the "V3:sq=…" formatting to the rendering seam (the same probe-event module as Candidate 2). The pure solve result stops owning display.

  • Locality — display formatting concentrates at the render seam, not inside solver math.
  • Leverage — typed per-hop state is a reusable input to the Candidate-2 event, not a dead string.
  • Testability — the result is comparable as data; no string-equality asserts.

ADR alignment — compatible; the fix folds into Candidate 2's probe-event module.

No conflict with ADR-015 (the seam composition is untouched; only the result's payload shape changes). Best taken together with Candidate 2 so one render seam owns both.

Top recommendation

Start with Candidate 1 — the solve seam's liquidity-clock gap. It is the one with a documented, currently-firing failure class (0x5653, staged price-fresh / map-stale) that the price-clock-only tripwire provably cannot see, and the fix is a focused addition to a settled seam (ADR-015) with a clean unit-test seam at the dispatch guard — no new script, no new tooling.

Candidate 2 follows as the reproducibility deepening. Once the state-accuracy event has a typed home, the 7 Python regex parsers and the bespoke per-recurrence capture/fixture/harness machinery collapse behind one seam. Candidate 3 is a small slice of the same render seam — take it together with 2 rather than alone.

Candidates 1 and 2 are independent. 1 makes the solve refuse a stale map; 2 makes the diagnosis reproducible. Neither re-opens a settled ADR-015 / ADR-020 / ADR-021 decision.
