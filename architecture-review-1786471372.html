Where the Rust core is shallow — and how to deepen it

A review of the recently-changed leaderboard of the degenbot-bot orchestration crate and its degenbot-order-index sibling, read through the /codebase-design lens (module / interface / depth / seam / leverage / locality). The block pump is the single most-churned slice of the codebase — block_pump.rs moved in 14 of the last 50 commits — and most of the friction below is concentrated there and in the solve path it drives.

4 candidates 1 Strong 2 Worth exploring 1 Speculative

1 · The per-family projection in resolve_path is a wide flat match

Strong

Files

degenbot-bot/src/solvers/arb_engine/solver_dispatch.rs — resolve_path (~470 lines) + the solver intake types in degenbot-solvers/src/mixed/* (ResolvedMixedPath, ResolvedHop, SolidlyHopState…).

Recommendation

Colocate each DEX family's "project BotState → solver hop-state" projection into that family's own module, and give the whole step a typed Option/Result instead of a mid-loop silent return.

Problem

resolve_path is the single flat match pool_ref.hop_type that walks every family — V2, V3, V4, SolidlyStable (which itself splits Aerodrome vs Camelot with a duplicated token-decimals lookup), plus the balance-vector arms — interleaving five concerns per family: identity lookup, state lookup, token-decimals resolution, swap-orientation, and solver-type construction. Each arm ends in let Some(…) else { return; } — a failed lookup silently invalidates the whole path mid-loop, after earlier hops were already pushed. This is a shallow interface: the function reads many different BotState accessors (get_v2_pool_state, build_int_v3_sequence, token_entry, …), and its contract is "construct this, or quietly refuse the path."

The seam is already decided (ADR-015): resolve_path is the degenbot-bot core-bound projection and must stay there. This candidate refines how the projection is structured internally — it does not move it crate-ward and does not re-litigate ADR-015. The deletion test passes: pulling each family's projection into a family-local module concentrates each family's projection + its decimals/orientation/fee logic in one place, rather than scattering it as interleaved arms.

Before · flat projection

solver_dispatch.rs one match hop_type · every family interleaved
V2 arm · identity+state+orient → IntHopState
V3 arm · identity + build_int_v3_sequence(24) → seq
V4 arm · identity + twin sequence + debug dump
SolidlyStable arm · Aerodrome / Camelot (decimals ×2)
balance-vector arms · …
failed lookup ⇒ return mid-loop, path silently invalid

After · per-family projection

resolve_path — thin dispatcher matches family → delegates → assembles ResolvedMixedPath, collects a typed error/none
V2 module · IntHopState::from(&BotState, ref)
V3 module · sequence builder + debug dump
V4 module · twin
Solidly module · Aerodrome/Camelot once, shared decimals
balance-vector module(s)
missing piece ⇒ typed Result/Option, reasoned per-family

Benefits (locality · leverage · tests)

  • Locality: adding a DEX family, or debugging one (e.g. the recent V4-clamp/V4-alignment churn that keeps landing in this exact file), becomes a single-family edit instead of a scan-and-patch of one long match.
  • Leverage: resolve_path shrinks to a dispatcher whose interface ("give me the hop-state for this pool ref, or say missing") is far smaller than today's interface (a dozen BotState accessors reachable from one place).
  • Tests: each family's projection is today only exercised end-to-end through the engine. A per-family module gets its own unit tests (orientation, decimals, fee-inversion, missing-pool) without standing up a full engine + registered path.

2 · The ArbitrageEngine path registry is five maps that must stay consistent

Worth exploring

Files

arb_engine/{mod,solver_dispatch,delivery_policy,lifecycle}.rs — the engine's derived state + rebuild_and_solve_affected (~235 lines).

Recommendation

Extract the reverse-index + dirty-set traversal behind a deep PathRegistry module owning add / remove / affected-traversal, so the engine stops hand-maintaining every derived map.

Problem

The engine holds five mutually-conditional derived structures — path_pools (path → pools), pool_to_paths (reverse index), path_resolved, results, pending_new_paths + last_solved_path_ids — plus a phase FSM (EnginePhase), and registration/removal must update several of them together (delivery_policy.rs:298 "Removes the path from the solve state (path_pools, pool_to_paths…)"). The invariant "these maps are mutually consistent" is a real, delicate contract — but it is embedded, not named. rebuild_and_solve_affected orchestrates index traversal → re-resolution → rayond solve → CL-clamp → result merge and maintains the change-set bookkeeping, all in one &mut self method.

The reverse-index and dirty-set traversal are cleanly separable from the solver math. The deletion test: a PathRegistry would concentrate the consistency invariant in one deep module (its interface is the invariant), where today it is smeared across three files and only tests.rs can prove it.

Before · consistency smeared

mod.rs — the 5 maps + phase fsm
lifecycle.rs — register writes path_pools + pool_to_paths
delivery_policy.rs — deregister removes path_pools + pool_to_paths
solver_dispatch.rs — rebuild_and_solve_affected touches path_pools, path_resolved, results, pending_new_paths, last_solved_path_ids
tests.rs — only place the invariant is asserted

After · deep PathRegistry

PathRegistry — one owner of path_pools + pool_to_paths + pending
lifecycle.rs — registry.register(path) (one call)
delivery_policy.rs — registry.remove(id) (one call)
rebuild_and_solve_affected → registry.affected(v2,v3,v4) then solve clamped into results
unit tests on PathRegistry — add/remove/traversal alone

Benefits (locality · leverage · tests)

  • Locality: "when is map X and map Y updated together?" has one answer (in PathRegistry) instead of three.
  • Leverage: rebuild_and_solve_affected shrinks to "ask the registry for the affected set + the change-set, solve, commit" — the engine stops owning index bookkeeping.
  • Tests: the add/remove/affected-traversal invariant is testable directly on the registry in isolation (Red→Green), instead of only through the whole engine; the ADR-021 change-set accumulation moves inside too.

3 · block_pump.rs is four lifecycles in one 4.7k-line file

Worth exploring

Files

degenbot-bot/src/bot_core/block_pump.rs — 4,738 lines; ~2,110 impl lines + ~2,610 lines of inline mod tests. Hot spot: 14 commits in the last 50. The decision state already moved into pump_fsm.rs (ADR-028); the rest has not.

Recommendation

Split the genuinely-separable lifecycles into sibling modules — the WS session/handshake lifecycle, the solver-state verifier task, and the backfill engine — and split the monolithic inline test module into per-module tests.

Problem

One BlockPump struct + one file holds four distinct lifecycles with different liveness rules and different change-drivers: (a) the WS session/handshake (subscribe, subscribe_with_stream, observe_complete_block, resume_from_subscribe, drain_stream_during_backfill); (b) the steady-state drain dispatcher (run_with_stream, ~730 lines — the thin driver the FSM feeds); (c) the solver-state verify loop (solver_state_verify_loop → verify_solver_state_against_chain, ~290 lines) which already runs on its own spawned task with its own latest-wins watch channel; (d) the backfill engine (backfill_range, backfill_to_ws_block, backfill_from_snapshot).

The verifier loop is the cleanest split — it is a self-contained subsystem (dedicated task + channel), so the deletion test passes: pulling it out concentrates its logic, it is not just moving it. The WS-handshake and backfill are more entangled with the drain cursor, so those splits are lower-confidence. The 2,610-line inline test module is the other locality problem: its hand-rolled FakeDrainSink / pump_for_test* / bot builders are trapped inside mod tests and cannot be reused by a sibling module's tests.

Before · one god-file

struct BlockPump (session cfg + io toggles + deps)
session · subscribe / observe_complete_block / resume
run_with_stream dispatcher (~730 lines)
verify · solver_state_verify_loop + verify_solver_state_against_chain (~290)
backfill · range / to_ws / from_snapshot
mod tests (~2,610 lines, helpers trapped inside)

After · sibling modules

ws_session.rs · handshake lifecycle
block_pump.rs · struct + run_with_stream driver (+ pump_fsm)
solver_state_verifier_task.rs · spawned loop + watch channel
backfill.rs · the three backfill entry points (shared test helpers)
per-module tests + a shared test_util for FakeDrainSink/bot builders

Benefits (locality · leverage · tests) + honest caveat

  • Locality: the hottest file shrinks; each lifecycle's change driver commits into its own local module (session fixes land in ws_session.rs, verifier fixes in the verifier task module).
  • Tests: the verifier task and backfill become unit-testable in isolation, and the shared FakeDrainSink/bot builders stop being trapped inside one mod tests.
  • Caveat (honesty): the drag of a big file is real but partly cosmetic — the high-value extraction is the self-contained verifier task and the test-module decomposition. Splitting the entangled session<->backfill<->drain-cursor logic purely for file size would fail the deletion test (just moving complexity), so that part is lower-confidence.

4 · solver_state_verifier.rs: a stack of env-gated tripwires in one module

Speculative

Files

degenbot-bot/src/bot_core/solver_state_verifier.rs — 2,132 lines, of which ~1,900 are inline tests. Several separately-gated diagnostic probes as free functions.

Recommendation

Treat the ADR-021 fail-fast family as a set of seams: colocate each probe (its matcher + its env gate + its tests) in its own module, rather than stacking them as sibling free functions with sibling *_enabled() env-readers.

Problem

The module stacks at least four independently-config-gated diagnostic tripwires as flat free functions: divergence_scan_enabled, solve_anchor_probe_enabled, staged_clock_probe_enabled, plus a CL-staleness threshold (parse_cl_staleness_blocks / is_cl_pool_stale). Several are OFF by default and carry probe_default_off_single_env_get tests. These probes were added incrementally (recent commits: "staged-clock probe on the solve-time skip-in-progress path", "solve/verify anchor at the settled block"). Each is a small shallow module glued to its own predicate cluster (is_lagging_tracked, is_future_price, skip_in_progress_hop, …).

The friction is discoverability: a future explorer / AI must parse which predicate belongs to which gated probe, and the env-flag to turn it on, all from one dense module. This is the weakest of the four candidates (hence Speculative) — the code is not buggy, just undifferentiated, so the deletion-test case ("concentrates, doesn't just move") is real but mild.

Before · flat probe stack

divergence_scan · enabled() + predicates
solve_anchor_probe · enabled() + advancement consensus
staged_clock_probe · enabled() + skip-in-progress
CL-staleness · parse threshold + is_stale/isfuture
~1,900-line inline test module

After · probe per module

probes/divergence.rs · gate + matcher + tests
probes/solve_anchor.rs · gate + consensus + tests
probes/staged_clock.rs · gate + skip + tests
probes/cl_staleness.rs · threshold + predicates + tests
verifier.rs · the one always-on ADR-021 publish-point check

Benefits (locality · tests)

  • Locality: "which env flag enables this tripwire, and what are its rules?" answers itself per-probe module.
  • Tests: each probe's gate-behaviour + matcher tests live beside it, shrinking the 1,900-line inline test module and letting a probe be understood (and toggled) in isolation.

Top recommendation — start with Candidate 1

Per-family resolve_path projection is where I'd begin, for three reasons. It is the only Strong candidate: the deepening is real and self-contained (split one long match, give the step a typed result), it is not pre-empted by an ADR (ADR-015 only fixes where the projection lives, not how it is built), and it pays off immediately because this exact file keeps absorbing the churn — the V4-clamp/V4-alignment convergence fixes, the terminal-V2 exact-out fix, the CL-hop capacity clamp — all the recent "align the hop output to the twin" work lands in solver_dispatch.rs.

Candidate 1 also unlocks the others: it's the front half of the solve path, so its per-family modules give the PathRegistry (Candidate 2) a clean place to hand a family-indexed projection. I'd do 1 → then the verifier-task extraction half of 3 → then 4 if the tripwires keep growing. The entangled session/backfill half of Candidate 3 I'd leave alone until a real forcing function appears — it would fail the deletion test today.

Detail: the per-family projection currently carries a let Some(…) else { return; } silent-invalidation pattern; any deepened module should convert that to a typed Result/Option so a missing pool is a reasoned unit, not a mid-loop bail. This is Red→Green territory: write the per-family unit tests first (orientation, decimals, fee-inversion, missing-pool) pinned to the current end-to-end behaviour, then split.
